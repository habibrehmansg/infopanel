# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository, for branch **`2.0.x`**: InfoPanel 2.0, one cross-platform .NET engine (Windows and macOS) that renders sensor dashboards with SkiaSharp and serves a REST API, a live preview socket and a browser editor's static files on localhost. No web client is built from this repository: the engine serves the built client that `--web-root` points at, or `wwwroot` next to the engine, else the API only. 1.x (the Windows-only WPF app) ships from branch `1.4.x`; its code is not on this branch (read it with `git show 1.4.x:<path>`; `PORTING.md` lists what still has to come over).

## Branch rules

- Commit directly to `2.0.x`; no PRs until 2.0 is release-ready. No worktrees.
- No CI on this branch: `.github/workflows/dotnet-desktop.yml` is 1.x's and doesn't trigger on `2.0.x`. Don't touch `.github/`. Run the checks below yourself.

## Commands

From the repo root:

```bash
dotnet build InfoPanel.slnx
dotnet test InfoPanel.slnx
dotnet test InfoPanel.slnx --filter Category=Golden            # renderer goldens only
dotnet test InfoPanel.slnx --filter "FullyQualifiedName~Preview"
dotnet test InfoPanel.slnx -c Release --filter Category=Performance --logger "console;verbosity=detailed"   # timings, p50/p95/p99
# Opt-in: the built engine as a child process, SIGKILLed at seeded random points and restarted on the same folder
# (Unix only; INFOPANEL_CRASH_KILLS, default 50, and INFOPANEL_CRASH_SEED, logged by every run, repeat or extend it)
INFOPANEL_CRASH_TESTS=1 dotnet test InfoPanel.slnx --filter FullyQualifiedName~CrashKillTests

# Engine for development: port 5199, data in ./.data, a web client's dev-server origin http://localhost:5180 allowed, mock sensors
dotnet run --project InfoPanel --launch-profile dev
# Engine as users run it: default data folder, opens the browser; a source build has no wwwroot, so without --web-root it serves the API only
dotnet run --project InfoPanel -c Release
dotnet run --project InfoPanel -c Release -- --web-root <dir>  # serve a built web client (the folder with its index.html)
dotnet run --project InfoPanel -- --help                       # all flags
```

Engine flags: `--port`, `--data-dir`, `--web-root`, `--token`, `--dev-origin` (repeatable), `--allow-origin <origin>` (repeatable; an exact `scheme://host[:port]` origin of a web client served elsewhere, `https` unless the host is loopback, see the security model), `--fresh`, `--mock`, `--mock-seed` (implies `--mock`), `--no-browser`, `--no-windows` (no desktop windows). `--fresh` is a dev and test flag that wipes the whole data folder before start-up: it needs `--data-dir`; it refuses a filesystem root, the home folder or a folder above it (checked on the path as given and on its real path, links resolved) and a folder with any top-level entry the engine doesn't write (`store.json`, `profiles.json`, `tokens.json`, `settings.json`, `profiles/`, `blobs/`, `fonts/`, `logs/`, `runtime.json`, `engine.lock`, step-1's `profiles.xml` and `assets/`, the 1.x migration's `import-v1.json`, their write temp files); otherwise it deletes everything in the folder except `engine.lock`, including whatever is inside those engine folders (user-added fonts too), removing links without following them. The web root is `--web-root <dir>` as given, else `{BaseDirectory}/wwwroot` when it has an `index.html`; with neither the engine serves the API and `/ws`, and a plain-text "no web client installed" page on unmatched non-file paths outside `/api`, `/ws` and `/auth` (file-like paths such as `/index.html` or `/missing.js` return 404). `--mock` is mock mode: the mock sensors instead of the platform's real ones, and simulated values for well-formed keys no source handles; without it unknown keys are `unavailable` (the `dev` launch profile and every test host pass it). Exit codes: 0 clean, 1 fatal (a data folder whose marker this engine can't honour included), 2 bad arguments, 3 data folder in use. The sign-in link (`/auth/<token>`) and each `--allow-origin`'s pairing link go to the console only (the file log and the recent entries get them with `<token>`).

## Architecture

- **One engine, browser UI.** The engine runs headless on `127.0.0.1:{port}` and serves the API, `/ws` and the web root's static files (`index.html` for every non-file path outside `/api`, `/ws` and `/auth`). A client only edits through the API and only shows engine frames; it has no model or renderer of its own.
- **REST** (`/api/...`, exactly `spec/docs/api.md` and `commit.md`; bodies are the `InfoPanel.Spec` model written with `SpecJson.Options`): session (`protocol: 2`, `instance`, `features` (none yet), `formatSupport` by format string, each with its version, capabilities and limits, `platform`, `dataDir`, `locale` (the PC's regional format read at start-up)), fonts, sensors (by key, with `status`) and values, profiles (list with statuses `ok`/`unsupported`/`unreadable`, create empty or from a document under a client-chosen id, duplicate, delete), a profile's document (`GET /api/profiles/{id}`: `documentResponse`), export (`GET …/document`), thumbnail, commit, undo, redo, revert, save, blobs (`POST`, `HEAD`, `GET /api/blobs/{id}`), and integration tokens (`POST`, `GET /api/tokens`, `DELETE /api/tokens/{id}`; session token only). A request on a profile is checked in order: 404, 409 `profileStatusProblem`, 422, then its own checks (409 `exists`, conflicts, `expired`). Errors are `application/problem+json`. The step-1 editing API (`/api/kinds`, `items/*`, `PATCH` profile, `.infopanel` import and export) is gone.
- **`/ws`**: the client subscribes to a profile at a scale and fps; the server sends `hello` (`protocol: 2`), `doc` events (`docEvent`: `rev`, `dirty`, `canUndo`, `canRedo`; a coalesced latest-state slot, after every change from any client, and after the process history budget evicts the document's steps), `profiles` events, and binary frames (`IPF1`, the `frameHeader` of `api.md`: `rev`, `tick`, `frameId`, `scale`, sizes and `itemBounds` from one tick snapshot, then a PNG). A frame is sent only when pixels, bounds or revision changed; ticks never go down within a subscription.
- **Rendering**: `RenderService` runs one `RenderLoop` per subscribed profile, each holding a `SceneRuntime` that loads every new generation of the document (`ProfileDocument.Current`, read without the document's lock); each tick takes one `TickSnapshot` (sensors through `SensorSceneInputs`, media through the process-wide `MediaSampleCache` over the blob store), draws it once per requested scale (`FrameScale`: the sizes `api.md` specifies), adds the stats overlay when the profile's `statsOverlay` is set, and hands the same `RenderedFrame` to every `IFrameSink` (the `/ws` preview and desktop windows now; panels later). A thumbnail (`RenderService.RenderOnce`, `GET .../thumbnail`) of a profile with a live loop draws the loop's latest snapshot without advancing it (no stats overlay), so at the profile's width it equals the live frame; with no loop it draws a one-off `Snapshot(now)` of the current generation.
- **Scene runtime** (`InfoPanel.Core/Scenes/`, behind every output): `SceneRuntime.Load(Generation)` loads an already-checked `InfoPanel.Documents.Generation`, reusing its checked and compiled scenes by identity, so a commit costs only what it changed (one checked with other limits or support is checked again with the runtime's; `Load(JsonElement)` checks a `infopanel.document/1` into a generation first: each scene validated on its own, placeholders for the rest); snapshots carry the generation's `Rev`; `Tick(elapsed, now)` reads every input once, evaluates values, state cells (keyed by item, cell name and canonical definition) and text layout in the two phases of `spec/docs/expressions.md`, takes the media frames, and returns a reference-counted `TickSnapshot` that `Draw(canvas, scale)`, `Render`, `Bounds` and thumbnails share; `Snapshot(now)` is the one-off render (cells at init, elapsed 0). Each tick's clock carries the regional format `format` and `formatTime` use (`RegionalFormat`): the profile's `locale` (looked up with no user overrides; an unknown tag falls back and is logged once per process; the lookups and the logged tags are kept in small bounded caches), else the PC's, which `Program.cs` reads once at start-up (`PcRegionalFormat.Read`: CoreFoundation on macOS, whatever the launch environment, .NET's current culture elsewhere) and passes as `SceneRuntimeOptions.Locale`; nothing reads the process culture. Budgets at run time (work, text layouts, dashes, a time watchdog, the process node budget) draw an item as a `budget` placeholder with a diagnostic. `SceneRender` is the internal entry point for tests. Timings: `dotnet test InfoPanel.slnx -c Release --filter Category=Performance --logger "console;verbosity=detailed"`.
- **Desktop windows** (`InfoPanel/Desktop/`, 1.x's `DisplayWindow`): `DisplayWindowManager` (hosted service) keeps one borderless window per profile whose `profile.window.enabled` is true, each an `IFrameSink` at scale 1 (one frame pixel per backing pixel; a profile over the 16-megapixel frame cap renders smaller and the window stretches it to fill) and the frame rate setting (`frameRate`, 15 by default; a change re-times every window's loop at once, without reattaching), and applies the profile's size and its `window` (`topmost`, `draggable`, `resizable`, `x`/`y` in pixels from the display matched by `display`, `strict`; 1.x's rules) as they change, undo and redo included. A drag or resize of the window is a `profile` commit with a `gesture:` coalescing key of its own and the revision it read as `baseRev`, read again and retried on a conflict so another client's window change is kept (undoable, saved by Save). On macOS AppKit runs on the process main thread: `DesktopHost` runs the host on a worker and `-[NSApplication run]` on the main thread until the host stops; with `--no-windows`, off the main thread (test hosts) or on Windows/Linux (not ported yet) the platform is `NullDesktopPlatform` and nothing opens. Manager state lives on the UI thread (`IDesktopPlatform.Post`). `INFOPANEL_WINDOW_TESTS=1 dotnet test InfoPanel.slnx --filter FullyQualifiedName~MacDesktopWindowTests` opens real windows (skipped otherwise).
- **Storage and editing**: `InfoPanel.Documents.Workspace` (Core) is started once (`Workspace.Start`): the data folder's marker checked, both stores opened, the blobs swept, then the first change: on a first run (the store didn't exist) the example for the platform and sensor source (`Workspace.FirstRunExamples`: "Mac overview", 800×480, on macOS with the Mac's own sensors; "Wide bar" with `--mock`, whose sensors it shows, and elsewhere), the blobs it names stored first as an upload stores them (hash checked; an example one of whose blobs can't be stored is skipped and logged). It lists the store's profiles with their status, opens a document the first time anything reads it and keeps it open until it is deleted or the engine stops (then disposed), and checks create and duplicate bodies. A profile's id is its folder's name: a stored document with another `id` is opened under the folder's and saved with it. A profile that isn't `ok` is checked once per run and never rewritten. One lifetime per document: storing a new profile with publishing its document, opening, and deleting from the store with disposing its document each run under the workspace lock as one step, so a deleted document is disposed (its save finished, none after) before its id can be created again; whatever acts on a document later (a render loop through `RenderService.Attach(sink, document)`, a `/ws` subscription, a desktop window) holds the instance it found and treats it as deleted once `Workspace.IsOpen` is false. Each `ProfileDocument` (`Documents/`) applies commits, undo, redo and revert as in `spec/docs/commit.md` (one transaction under its lock; field revisions; coalescing keys: `gesture:` always merges, other keys within 1 s; per-document and process-wide history caps), with exact dirty; save writes the current generation to its `document.json`. Unsaved changes are lost on restart.
- **Settings** (`InfoPanel.Core/Settings/`): `SettingsStore`, opened at start-up after the workspace, keeps the engine settings in `settings.json`: `format` (`infopanel.settings/1`) and only the members someone set, each absent one at its default (1.4.x's: `frameRate` 15 (1–60), `graphRate` 1000 ms (100–3000), `logLevel` `information`, `sources.libre` on, storage on, `storageInterval` 30 s (1–300); `clients.{name}`, a client's own preferences, at most 16 of 64 KiB). `Apply` merges a change (`null` removes a member), refuses unknown members and out-of-range values with every error at its path, writes at once with `AtomicFile` and raises `Changed` with a run-local `version`; a change that leaves the content as it is writes nothing. Unknown members in the file are kept at any depth; a stored known member that breaks its rule gets its default with a warning. A file that can't be read (over 1 MiB, not JSON, no `format`) or of another major version leaves the defaults in effect, is logged and is never rewritten in that run: every change is refused. The 1.x settings reader clamps the rates and interval to these ranges with an `import.setting` warning. Live consumers: desktop windows ask for `frameRate` (the `/ws` preview keeps its own `maxFps`, 30 when absent), and `SensorHistory` samples every `graphRate` ms (re-timed on a change, samples kept); the engine's logger follows `logLevel`.
- **Sensors**: `SensorHub` over `ISensorSource`s: in mock mode `MockSensorSource` only, with a deterministic simulated walk for unknown well-formed keys; otherwise the platform's real source (macOS: `MacSensorSource`, keys `plugin:/infopanel.macos/{group}/{sensor}`; none on Windows and Linux yet) and unknown keys are `unavailable`. Statuses (`SensorStatus`): `live`, `stale` (last value kept), `unavailable`, `denied`, `simulated` (mock mode), `missing` (unbound or malformed); `/api/sensors` and `/api/sensors/values` carry `status`, and `SensorSceneInputs` maps them to scene input statuses as `spec/docs/bindings.md` states. Real sources are `PolledSensorSource`s over an `ISensorSampler`: discovery on start (the host's `SensorService` waits up to 5 s for every source's discovery before the server starts, so the first `/api/sensors` is complete; a slower source is logged and finishes in the background), a poll a second on the thread pool, stale after 5 s without a good sample (or right after a failed read), unavailable after 30 s. `INFOPANEL_SENSOR_TESTS=1 dotnet test InfoPanel.slnx --filter FullyQualifiedName~MacSensorSourceTests` reads the real macOS sensors (skipped otherwise). Each tick snapshot reads every input once.

## Invariants

- **Preview = panel.** A client never renders; frames come from the runtime's tick snapshot, and `PreviewParityTests` (host) holds the WS frame to a direct draw of that snapshot and to a panel-style sink on the same loop, pixel for pixel, on a 2.0 document.
- **Model freeze: superseded for storage.** The engine stores 2.0 documents (`Documents/`); 1.x profiles and `.infopanel` files are import-only, and the 1.x models, XML and archives are read only by the 1.x code kept for that import and for the parity oracle. That code still keeps its rule: never add, remove or rename a public read/write property or public field on the models (`InfoPanel.Core/Models`), and the XML stays readable by 1.x.
- **Rendering never writes to the document**: a generation and everything reachable from it is immutable; per-item state lives in the runtime, and render time, inputs and media come only from the tick snapshot, so goldens and parity stay deterministic. (The 1.x renderer keeps its own rule: time, sensors and history only from `RenderContext`, per-item state in `ItemStateStore`.)
- **1.x files load or fail loudly**: unknown item types (newer 1.4.x builds) and `xsi:nil` items are dropped with a warning; unreadable XML throws and is never overwritten.
- **Undo, redo, dirty and save belong to the engine**; don't reintroduce client-side history.
- **The kind manifest snapshot is the 1.x item JSON**: `InfoPanel.Core.Tests/Snapshots/kinds.json` (`KindManifestTests`) is the item JSON of the 14 1.x kinds that a 1.x import reads; the engine no longer serves it. Change it only with the models or `PropertyMap`, and review the diff.
- **The engine API is a contract.** `spec/openapi.json` lists every request the engine serves and every status each answers, and the host tests hold the engine to it both ways: a new or changed endpoint, status or body changes `openapi.json`, `docs/api.md`'s request table (one row per operation) and the tour (`InfoPanel.Tests/Contract/ContractTourTests.cs`) with it. Every JSON body is a schema definition with a `[SpecDef]` model, written with `SpecJson.Options`.
- **The formats are a contract, frozen at the first engine release.** `spec/` (schemas, docs, examples) is versioned: until that release every format in it is a draft; the release freezes them all at once, limits and error codes included (`spec/docs/versioning.md`, "What freezes"), and after it a change is made only as `versioning.md` allows. Every change comes with a regenerated `spec/types/index.d.ts`, examples for what changed (valid ones and an invalid one per new rule or limit, with `expected.json`) and the `InfoPanel.Spec` model and validators changed with it (`SpecSchemaAgreementTests`). The engine validates with the schema files themselves (embedded from `spec/schemas`), so there is one description of the formats. Public `spec/` text stays client-neutral: it specifies content and engine behaviour, never how a client produces it.
- **A minor version ships with `versioning.md`'s checklist** ("Shipping a minor version"). In this repository: the capability in `versioning.md`'s table and in the engine's capability sets (`Spec/Validation/Validation.cs`, with the validator's `requires.missing` check), the schema with the version and capability in its description, the docs, a valid example and an invalid one per rule or limit in `expected.json`, `npm run gen`, and the format's minor version in `formatSupport` (`Api/ReadEndpoints.FormatSupportOf`). A new limit goes in `SpecLimits` and under its format (`SpecLimits.FormatOf`); an operation added after version 1 of the API, under a name in `ReadEndpoints.Features`.
- **Closed where the engine interprets, tolerant where a client reads it** (`versioning.md`, "Unknown members and values"). Content, request bodies and the socket's client messages refuse members they don't define (`PreviewSocketHandler.ClientMessageMembers` is the schema's list, `SocketConformanceTests` holds them equal); what the engine sends is read tolerantly (`FrameCodec.Decode` skips header members it doesn't know), and every enumeration in it states a client's fallback in its description (`npm run check` fails otherwise).
- **Limits are fixed per major format version** (`InfoPanel.Spec.SpecLimits`, `spec/docs/limits.md`): an engine accepts everything within them.
- Plugin SDK projects stay on net8.0.

## Security model

- Kestrel binds 127.0.0.1 only and ignores configured URLs and endpoints. Host filtering allows `localhost`, `127.0.0.1` and `[::1]`; a request that carries an `Origin` (WebSocket upgrades included) must come from the engine's own origin, a `--dev-origin` or an `--allow-origin`; any other gets 403 and no CORS headers.
- Two token kinds (`Security/TokenStore.cs`, `Caller`). The **session** token is per start (random, or `--token`), has full access and is never stored. **Integration** tokens are created, listed and revoked through `/api/tokens` with the session token only; each has a name and scopes, `read` and/or `edit` (`edit` implies `read`); the secret is `ipi_` and 256 random bits in base64url, answered once by the create and never logged. `tokens.json` in the data folder holds each token's id, name, kind, scopes, `created`, `lastUsed` (written at most once a minute) and the SHA-256 of its secret, never the secret, written with `AtomicFile.WritePrivate` (0600); a presented token is hashed and compared with every stored hash in constant time. An unreadable `tokens.json` (over 16 MiB, not a regular file, or a token of a kind or with a scope it doesn't know) stops the engine at start-up (exit 1) instead of being dropped or overwritten; members it doesn't know are ignored and kept, as written, when it rewrites the file (compact), and a create that would take it over `tokensBytes` (16 MiB) is refused, 422 `limit.tokensBytes`.
- Scopes fail closed: every endpoint under `/api` declares one with `.RequireScope(ApiScope.Read|Edit|Session)` (reads `read`, every change to a document, blob or profile `edit`, the token endpoints `session`), `ScopeFilter` (after routing) answers 403 `scopeProblem` to a token without it, and an endpoint without a declaration is session-only; `TokenTests.EveryApiEndpoint_DeclaresTheScopeItsMethodNeeds` enumerates them all. A missing, unknown or revoked token is 401. `/ws` declares `read`. Revocation is immediate: the next request with the token gets 401, and every `/ws` connection authenticated with it is closed with 1008 and the reason `token revoked`.
- `/api` needs `Authorization: Bearer {token}` (either kind); `/ws` needs the subprotocol `infopanel.v1` and the token, either as the subprotocol `auth.{token}` (browsers can't set WebSocket headers) or, when no `auth.*` subprotocol is offered, as the first message `{"type":"auth","token":"…"}` within 5 s (a hard deadline for the whole phase, however the client streams fragments; the close handshake after it is bounded at 2 s): the server sends nothing before it and closes with 1008 and the reason `auth timeout`, `auth rejected` or `auth expected` otherwise (`PreviewSocketHandler`). Everything else is public: the web root's static files, `/healthz` and `/auth/{token}`. No cookies (a `localhost` cookie reaches every local server) and no CORS unless `--allow-origin`.
- `--allow-origin <origin>` (off by default) lets a web client served from that exact origin call the engine. It must be `https`, or `http` on a loopback host (`localhost`, 127.0.0.0/8, `[::1]`), since the pairing link hands it the token; `%` (escapes, IPv6 zone ids) is refused, and IPv6 hosts are stored as browsers serialise them (`[::ffff:127.0.0.1]` becomes `[::ffff:7f00:1]`). The origin gets CORS on `/api` and `/healthz` only (`Security/CrossOrigin.cs`: preflights answered 204 before the token check, the exact origin echoed, `Vary: Origin`, `Access-Control-Allow-Private-Network: true` when asked, never `Allow-Credentials`; 401s carry the CORS headers too), and its `/ws` upgrades pass the Origin check. The pairing link `{origin}/#engine=http://127.0.0.1:{port}&token={token}` hands that origin the engine URL and token in the fragment. The engine's own origin and the dev origins get no CORS headers.
- `GET /auth/{token}` accepts only the session token (an integration token gets 401, so it can never be exchanged for the session token), and the pairing links carry only the session token. It redirects to `/#token={token}`; the web client reads the fragment (never sent to a server), keeps the token in `localStorage` (per origin, so per port), removes it from the address bar and sends it as a Bearer token. The token is random per start unless `--token` is given.
- CSP, `X-Frame-Options: DENY`, `nosniff` and `Referrer-Policy: no-referrer` on every response; imports guard against zip-slip, entry-count and size bombs, and oversized profiles.

## Data folder

`{LocalApplicationData}/InfoPanel/v2`: `~/Library/Application Support/InfoPanel/v2` on macOS, `%LOCALAPPDATA%\InfoPanel\v2` on Windows (`--data-dir` overrides). Layout and rules: `docs/2.0/data-folder.md`. `store.json` is the folder's marker, `{"format":"infopanel.store/1","requires":[]}` (`Persistence/StoreMarker.cs`), written when absent: `Program` reads it, read only, before it creates anything in the folder (`StoreMarker.Preflight`, so a refused start leaves no `engine.lock` either; skipped with `--fresh`, which wipes it), again right after taking `engine.lock` (and after `--fresh`), before anything repairs, sweeps or writes there (the log folder included), and `Workspace.Start` again before the stores open; an unreadable marker, another major version or a `requires` capability the engine lacks (`StoreMarker.Capabilities`, none in 1.0) stops start-up with exit 1 and a message naming it, nothing in the folder changed and a lock file already there left in place. A later engine that keeps blob references outside the profiles' folders, or a rule an earlier engine must enforce, adds a store capability there. The 2.0 store: `profiles.json` (display order only, within its own bound `profileListBytes`: a create or duplicate past it is 422 `limit.profileListBytes`, and a larger file isn't read), `profiles/{id}/document.json` (each profile's saved document, `id` a lower-case UUID; the blob sweep's root rule: every file under each folder of `profiles/` at any depth, read through links (each real folder once), but OS metadata (`.DS_Store`, `._*`, `Thumbs.db`, `desktop.ini`) and write leftovers (`*.{32 hex}.tmp`), plus each folder's `document.json`; each is scanned as text for `sha256:` ids, as written and with JSON escapes decoded, JSON or not (a `document.json` must be JSON too), and one that can't be read, isn't a regular file, or a link whose roots can't be read stops that run's deletions, so what a later engine keeps there keeps its blobs), `blobs/{64 hex}` (media and other blobs by SHA-256; a blob's file is hashed on its first read in a run, the verdict cached per file length and last-write time (at most 4096 verdicts, the least recently used dropped first), a profile export hashes every blob it archives, and a file that doesn't hash to its id counts as not stored until the right bytes are uploaded again); and `fonts/` (user fonts; Inter is bundled), `logs/infopanel-{yyyyMMdd}.log` (`Hosting/EngineLogFile`: 100 MiB a file, the newest 7 kept; a target that isn't a regular file turns the file log off for the run, with one console warning), `runtime.json` (pid, port and URL while running: a hint, since a crash leaves it; liveness is the lock and `GET /api/session`), `tokens.json` (integration tokens, hashes only, 0600), `settings.json` (the engine settings, only those set; `infopanel.settings/1`), `engine.lock`, `import-v1.json` (the 1.x migration's run-once record). The engine's own files (`profiles.json`, `tokens.json`, `import-v1.json`, `settings.json`) are read tolerantly: members it doesn't know are ignored and kept when it rewrites them (`Persistence/EngineJson`: as JSON text, compacted, so any value survives; settings as values), within each file's byte cap (`tokens.json` `tokensBytes`, 16 MiB); each is read at `jsonDepth` (settings at its own 64); one the engine can't hold whole (over its cap, too deep, not a regular file) is never rewritten, and the run does without it (the order in memory, the record counted as done, tokens stop the engine). Every open and listing in the data folder goes through one layer (`Persistence/RegularFile`, data-folder.md "Special files and links"): only regular files are opened (non-blocking, the type checked on that handle; on Windows by literal `\\?\` name, so `NUL` is a file), so a FIFO or device never blocks start-up (the lock, fonts and the log file included); a link whose target can't be reached is never "absent" or "empty" (the sweep deletes nothing; the data folder, `profiles/`, `blobs/`, `engine.lock` or `tokens.json` stops start-up with exit 1, nothing written; a profile folder that is one stays listed, unreadable); every listing is bounded (1,000,000 entries; the sweep 250,000 entries and 1 GiB in all, past which it deletes nothing). Step-1 data in the same folder (`profiles.xml`, `profiles/{guid}.xml`, `assets/{guid}/`) is left untouched and unread, with one warning at start-up. 1.x's own data (`%LOCALAPPDATA%\InfoPanel`) is never touched.

Durability (`AtomicFile`): every store file is written to a temp file, flushed, renamed over its target, and its folder flushed (every new folder into its parent). After an engine crash at any step each file is its previous version or its new one, never a mix, on every platform. After a power loss, on a drive that honours flush requests: on macOS a write that answered survives (the file and every folder get `F_FULLFSYNC`, which empties the drive's cache too; a file system that can't do it gets `fsync`, with one warning per process); on Linux it survives (`fsync` on file and folder); on Windows folders aren't flushed, so a save that answered can come back as the previous version and a new profile or blob can be missing, but no file is torn. The fault tests (`CrashSafetyTests`) prove the order of the steps, not lost drive caches.

## Conventions

- Logging: Serilog (see `LoggingGuidelines.md`). The engine's level is the `logLevel` setting (a `LoggingLevelSwitch`, live); `RecentLog` (`Hosting/`), a sink in the log file's branch, keeps this run's newest 2,000 entries (at most 2 MiB; messages cut at 4,096 characters, exceptions at 8,192, sources at 256), each with a `seq` from 1, for clients. `CrashLogging` logs unhandled exceptions (`Fatal`, then the log is written out) and unobserved task exceptions (`Error`).
- Tests pin culture, time and the PC's regional format (`SceneRuntimeOptions.Locale`: the invariant format in the Core kits, en-US in `EngineFactory`); goldens and other process-wide font state run in the non-parallel `Golden` collection.
- Docs for 2.0 live in `docs/2.0/`; `PANELS.md`, `PLUGINS.md` and `PLUGIN-ARCHITECTURE.md` still describe 1.x.

# CLAUDE.md

Guidance for Claude Code (claude.ai/code) in this repository, for branch **`2.0.x`**: InfoPanel 2.0, one cross-platform .NET engine (Windows and macOS) that renders sensor dashboards with SkiaSharp and serves a REST API, a live preview socket and a browser editor's static files on localhost. No web client is built from this repository: the engine serves the built client that `--web-root` points at, or `wwwroot` next to the engine, else the API only. 1.x (the Windows-only WPF app) ships from branch `1.4.x`; its code is not on this branch (read it with `git show 1.4.x:<path>`; `PORTING.md` lists what still has to come over).

## Branch rules

- Commit directly to `2.0.x`; no PRs until 2.0 is release-ready. No worktrees.
- No CI on this branch: `.github/workflows/dotnet-desktop.yml` is 1.x's and doesn't trigger on `2.0.x`. Don't touch `.github/`. Run the checks below yourself.

## Commands

From the repo root:

```bash
dotnet build InfoPanel.slnx
dotnet test InfoPanel.slnx
dotnet test InfoPanel.slnx --filter Category=Golden            # renderer goldens only
dotnet test InfoPanel.slnx --filter "FullyQualifiedName~Preview"
dotnet test InfoPanel.slnx -c Release --filter Category=Performance --logger "console;verbosity=detailed"   # timings, p50/p95/p99

# (Unix only; INFOPANEL_CRASH_KILLS, default 50, and INFOPANEL_CRASH_SEED, logged by every run, repeat or extend it)
INFOPANEL_CRASH_TESTS=1 dotnet test InfoPanel.slnx --filter FullyQualifiedName~CrashKillTests

# Engine for development: port 5199, data in ./.data, a web client's dev-server origin http://localhost:5180 allowed, mock sensors
dotnet run --project InfoPanel --launch-profile dev
# Engine as users run it: default data folder, no browser until asked (the menu bar's Open Editor, or starting it again); a source build has no wwwroot, so without --web-root it serves the API only
dotnet run --project InfoPanel -c Release
dotnet run --project InfoPanel -c Release -- --web-root <dir>  # serve a built web client (the folder with its index.html)
dotnet run --project InfoPanel -- --help                       # all flags
# A release build that opens a web client served elsewhere (its pairing link): the origin is built in, the default for --allow-origin
dotnet build InfoPanel -c Release -p:InfoPanelAllowOrigin=https://client.example
# The macOS app and its disk image, ad hoc signed (macOS only; --out a new or empty folder; docs/2.0/packaging.md)
packaging/macos/build.sh --version 2.0.0-beta.1 --allow-origin https://client.example --out <dir>
# Windows installer (on Windows, with Inno Setup 6): InfoPanel-<version>-win-x64-setup.exe in a new folder (docs/2.0/packaging.md)
powershell -NoProfile -ExecutionPolicy Bypass -File packaging\windows\build.ps1 -Version 2.0.0-beta.1 -AllowOrigin https://client.example -Out C:\builds\2.0.0-beta.1

The sign-in link (`/auth/<token>`, printed only when a web client is served here, since it leads nowhere otherwise) and each `--allow-origin`'s pairing link go to the console only (the file log and the recent entries get them with `<token>`). `--allow-origin`'s default is the origin a release build carries (the MSBuild property `InfoPanelAllowOrigin`, recorded as the assembly metadata `InfoPanel.AllowOrigin` by `InfoPanel/WebClientOrigin.targets`; none in a build from source), checked as the flag is; any `--allow-origin` replaces it.

## Architecture

- **One engine, browser UI.** The engine runs headless on `127.0.0.1:{port}` and serves the API, `/ws` and the web root's static files (`index.html` for every non-file path outside `/api`, `/ws` and `/auth`). A client only edits through the API and only shows engine frames; it has no model or renderer of its own.
- **REST** (`/api/...`, exactly `spec/docs/api.md` and `commit.md`; bodies are the `InfoPanel.Spec` model written with `SpecJson.Options`): session (`protocol: 2`, `instance`, `features` (`plugins`, always), `formatSupport` by format string (`infopanel.document/1`, `infopanel.scene/1`, `infopanel.archive/1`), each with its version, capabilities and limits (`SpecLimits.FormatOf`), `platform`, `dataDir`, `locale` (the PC's regional format read at start-up); for bug reports `engineBuild` (the commit the engine was built from, `-dirty` with uncommitted changes, `unknown` without git or a repository: recorded at build time by `RecordEngineBuild` in `InfoPanel/EngineBuild.targets`), `osVersion` (macOS's product version, Windows's major.minor.build, Linux's kernel release), `arch` (the engine process's) and `started` (the run's start, `EngineRuntime.Started`); `mock`, the run's mock mode or a replayed recording (`--replay-sensors`); `media.providers`, the media providers configured on the engine, `http`, and `rtsp` with FFmpeg), fonts, sensors (by key, with `status` and `type`, `number`, `text` or `table`, from the same hub read) and values, the sensor sources' states (`GET /api/sensors/sources`: every source the hub runs, in its order, with its state, reason and sensor count; `SensorHub.SourceStates`; Libre's entry with the PawnIO driver, `driver`, and its install, `POST /api/sensors/sources/libre/driver`, session token only: spec/docs/api.md "The PawnIO driver"), the engine settings (`Api/SettingsEndpoints.cs`, session token only: `GET /api/settings` answers `engineSettings`, every value with the run's `version` and the file's `status`; `PATCH` checks the body (409 `settingsStatusProblem` first when the file couldn't be read, then `settingsRequestBytes`, JSON and the schema) and hands it to `SettingsStore.Apply`, whose refusals are 422), the recent log entries (`Api/LogEndpoints.cs`, session token only: `GET /api/logs?after={seq}` answers `logPage`, `RecentLog`'s kept entries newer than `after`, oldest first, with `latest`, the run's newest `seq`, read together; an `after` that isn't 0–2^53−1 in decimal digits, or given twice, is 400), opening the engine's folders (`Api/FolderEndpoints.cs`, session token only: `POST /api/folders/{folder}/open` hands the data folder (`data`), `logs/` (`logs`) or `plugins/` (`plugins`, created when absent, never through a link: a link there is 500) to `IFolderOpener`, `Hosting/FolderOpener.cs`: `open` on macOS, `explorer.exe` on Windows, `xdg-open` elsewhere, the folder its one argument, refused when it isn't a folder; ## Invariants

- **Preview = panel.** A client never renders; frames come from the runtime's tick snapshot, and `PreviewParityTests` (host) holds the WS frame to a direct draw of that snapshot and to a panel-style sink on the same loop, pixel for pixel, on a 2.0 document.
- **Model freeze: superseded for storage.** The engine stores 2.0 documents (`Documents/`); 1.x profiles and `.infopanel` files are import-only, and the 1.x models, XML and archives are read only by the 1.x code kept for that import and for the parity oracle. That code still keeps its rule: never add, remove or rename a public read/write property or public field on the models (`InfoPanel.Core/Models`), and the XML stays readable by 1.x.
- **Rendering never writes to the document**: a generation and everything reachable from it is immutable; per-item state lives in the runtime, and render time, inputs and media come only from the tick snapshot, so goldens and parity stay deterministic. (The 1.x renderer keeps its own rule: time, sensors and history only from `RenderContext`, per-item state in `ItemStateStore`.)
- **1.x files load or fail loudly, and are only read**: unknown item types (newer 1.4.x builds) and `xsi:nil` items are left out with a diagnostic (`import.itemType`, `import.nil`); XML is read through `SafeXml` (no DTDs, bounded depth, elements and bytes) and unreadable XML is reported, never overwritten; nothing is ever written into the 1.x folder (`TheFolder_IsNeverWritten_ByAnyRead`, `The1xFolder_IsNeverWritten_ByAnyRequest`).
- **Undo, redo, dirty and save belong to the engine**; don't reintroduce client-side history.
- **The kind manifest snapshot is the 1.x item JSON**: `InfoPanel.Core.Tests/Snapshots/kinds.json` (`KindManifestTests`) is the item JSON of the 14 1.x kinds that a 1.x import reads; the engine no longer serves it. Change it only with the models or `PropertyMap`, and review the diff.
- **The engine API is a contract.** `spec/openapi.json` lists every request the engine serves and every status each answers, and the host tests hold the engine to it both ways: a new or changed endpoint, status or body changes `openapi.json`, `docs/api.md`'s request table (one row per operation) and the tour (`InfoPanel.Tests/Contract/ContractTourTests.cs`) with it. Every JSON body is a schema definition with a `[SpecDef]` model, written with `SpecJson.Options`.
- **The formats are a contract, frozen at the first engine release.** `spec/` (schemas, docs, examples) is versioned: until that release every format in it is a draft; the release freezes them all at once, limits and error codes included (`spec/docs/versioning.md`, "What freezes"), and after it a change is made only as `versioning.md` allows. Every change comes with a regenerated `spec/types/index.d.ts`, examples for what changed (valid ones and an invalid one per new rule or limit, with `expected.json`) and the `InfoPanel.Spec` model and validators changed with it (`SpecSchemaAgreementTests`). The engine validates with the schema files themselves (embedded from `spec/schemas`), so there is one description of the formats. Public `spec/` text stays client-neutral: it specifies content and engine behaviour, never how a client produces it.
- **A minor version ships with `versioning.md`'s checklist** ("Shipping a minor version"). In this repository: the capability in `versioning.md`'s table and in the engine's capability sets (`Spec/Validation/Validation.cs`, with the validator's `requires.missing` check), the schema with the version and capability in its description, the docs, a valid example and an invalid one per rule or limit in `expected.json`, `npm run gen`, and the format's minor version in `formatSupport` (`Api/ReadEndpoints.FormatSupportOf`). A new limit goes in `SpecLimits` and under its format (`SpecLimits.FormatOf`); an operation added after version 1 of the API, under a name in `ReadEndpoints.Features`.
- **Closed where the engine interprets, tolerant where a client reads it** (`versioning.md`, "Unknown members and values"). Content, request bodies and the socket's client messages refuse members they don't define (`PreviewSocketHandler.ClientMessageMembers` is the schema's list, `SocketConformanceTests` holds them equal); what the engine sends is read tolerantly (`FrameCodec.Decode` skips header members it doesn't know), and every enumeration in it states a client's fallback in its description (`npm run check` fails otherwise).
- **Limits are fixed per major format version** (`InfoPanel.Spec.SpecLimits`, `spec/docs/limits.md`): an engine accepts everything within them.
- Plugin SDK projects stay on net8.0.

## Security model

- Kestrel binds 127.0.0.1 only and ignores configured URLs and endpoints. The host rule (`Security/HostRule.cs`, a startup filter right after the security headers'; ASP.NET's host filtering is left open) allows `localhost`, `127.0.0.1`, `[::1]` and the `proxy.hosts` setting's names (at most 8 lower-case DNS names, `SettingsLimits.IsProxyHost`: a reverse proxy on this computer, such as Tailscale Serve), on any port, matched whole in any ASCII case on the `Host` header as received (`HttpRequest.Host` would decode an `xn--` name), the setting read at each request; anything else is 400 with no body. Forwarded and identity headers (`X-Forwarded-*`, `Forwarded`, `Tailscale-User-*`) are never read. A request carrying `Tailscale-Funnel-Request` (Funnel's mark on what it brings from the internet) is 403 whatever its host (`HostRuleStartupFilter`, before the host rule). A request that carries an `Origin` (WebSocket upgrades included) must come from the engine's own origin, a `--dev-origin` or an `--allow-origin`; any other gets 403 and no CORS headers.
- Two token kinds (`Security/TokenStore.cs`, `Caller`). The **session** token is per start (random, or `--token`), has full access and is never stored. **Integration** tokens are created, listed and revoked through `/api/tokens` with the session token only; each has a name and scopes, `read` and/or `edit` (`edit` implies `read`); the secret is `ipi_` and 256 random bits in base64url, answered once by the create and never logged. `tokens.json` in the data folder holds each token's id, name, kind, scopes, `created`, `lastUsed` (written at most once a minute) and the SHA-256 of its secret, never the secret, written with `AtomicFile.WritePrivate` (0600); a presented token is hashed and compared with every stored hash in constant time. An unreadable `tokens.json` (over 16 MiB, not a regular file, or a token of a kind or with a scope it doesn't know) stops the engine at start-up (exit 1) instead of being dropped or overwritten; members it doesn't know are ignored and kept, as written, when it rewrites the file (compact), and a create that would take it over `tokensBytes` (16 MiB) is refused, 422 `limit.tokensBytes`.
- Scopes fail closed: every endpoint under `/api` declares one with `.RequireScope(ApiScope.Read|Edit|Session)` (reads `read`, every change to a document, blob or profile `edit`, the token endpoints, the engine settings, the configured service, the recent log entries and the folder action `session`), `ScopeFilter` (after routing) answers 403 `scopeProblem` to a token without it, and an endpoint without a declaration is session-only; `TokenTests.EveryApiEndpoint_DeclaresTheScopeItsMethodNeeds` enumerates them all. A missing, unknown or revoked token is 401. `/ws` declares `read`. Revocation is immediate: the next request with the token gets 401, and every `/ws` connection authenticated with it is closed with 1008 and the reason `token revoked`.
- **Pairing** (`Security/PairingStore.cs`, `Security/PairingCodes.cs`, `Api/PairingEndpoints.cs`; spec/docs/api.md "Pairing"): a client served from another origin pairs by exchanging a one-time code (16 random bytes as 22 base64url characters, in memory only, at most 8 unused, each for 2 minutes) once at `POST /auth/pairing/code` (no token; CORS as `/api`, `CrossOrigin.AppliesTo`) for the run's session token and a lasting pairing, kept in `pairings.json` (id, name, times, its secret itself, since the engine proves the pairing with it; written with `AtomicFile.WritePrivate`, 0600, on Windows through a temp file from `IWindowsSecurity.CreateFile`). Uses are serialised (`PairingCodes.Redeem`); a second use is 403 with the first's text, removes the pairing the first made and logs a warning. `replaces` hands the client's old pairing over: unlisted, removed with its replacement, at the limit or 30 days after (checked at start and at each exchange); at most 32, replaced ones then the least recently used dropped. A file it can't read is logged as an error and never rewritten that run: `GET` and `DELETE /api/pairings` answer 409 and the exchange answers without a pairing. With `--port 0` the engine prefers the port the file keeps when it is free (`EngineRuntime.FindFreePort(preferred)`, logged when it isn't); the port is written with each pairing and at start (`EngineLifetime`) when pairings exist and it differs. The proofs (`Security/PairingProofs.cs`; `POST /auth/pairing/challenge` and `/proof`, no token, CORS as `/api`): for a pairing it has, a replaced one too, the engine draws Ne (32 bytes, a seam for tests: `NewNonce`), keeps the challenge 30 s, single use, at most 64 (the oldest dropped; a removed pairing's dropped with it) and answers `E = HMAC-SHA256(K, "InfoPanel pairing 1: engine" ‖ 0x00 ‖ Np ‖ Ne ‖ P)`, P its own listening port (`EngineRuntime.Port`, 2 bytes big-endian; never the `Host` header); the proof takes the challenge out and checks `C` (label `client`) in constant time, refusing a gone, expired, other pairing's or replaced pairing's challenge with one 403 text (a warning at most once a minute, with a count), then records the use (`lastUsed`, to within a minute) and answers the run's token and instance with `A` (label `answer`, over `token ‖ 0x00 ‖ instance` in UTF-8); 404 for a pairing it doesn't have (none when the file couldn't be read). Nothing logs a code, a secret, a nonce, a proof or the token (`PairingProofEndpointTests` scans the log); the test vector is spec/docs/api.md's (`PairingVectorTests`). `POST /api/pairings/codes` (session scope only) issues a code for a client on another computer (one reaching the engine through a reverse proxy on this computer): 201 `issuedPairingCode`, `{ code, expires, origins }`, `no-store`; the code is `PairingCodes.Mint`'s, so it shares the 8 and the 2 minutes with the link's codes and is exchanged once at `POST /auth/pairing/code`; `origins` is `EngineRuntime.CrossOrigins` (the `--allow-origin` origins, the only ones with CORS: not the engine's own or the dev origins; empty when none); "issued" is logged with its expiry, never the code. So a session token can mint lasting pairings (as it can integration tokens); no MCP tool declares `session`, and nothing in `InfoPanel.Mcp` or `RelayClient` holds `PairingCodes`, `PairingStore`, `EngineRuntime` or the service provider (`PairingEndpointTests.TheCodes_AreOutOfReachOfTheMcpToolsAndTheRelay`).
- `/api` needs `Authorization: Bearer {token}` (either kind); `/ws` needs the subprotocol `infopanel.v1` and the token, either as the subprotocol `auth.{token}` (browsers can't set WebSocket headers) or, when no `auth.*` subprotocol is offered, as the first message `{"type":"auth","token":"…"}` within 5 s (a hard deadline for the whole phase, however the client streams fragments; the close handshake after it is bounded at 2 s): the server sends nothing before it and closes with 1008 and the reason `auth timeout`, `auth rejected` or `auth expected` otherwise (`PreviewSocketHandler`). Everything else is public: the web root's static files, `/healthz` and `/auth/{token}`. No cookies (a `localhost` cookie reaches every local server) and no CORS unless `--allow-origin`.
- `--allow-origin <origin>` (off by default) lets a web client served from that exact origin call the engine. It must be `https`, or `http` on a loopback host (`localhost`, 127.0.0.0/8, `[::1]`), since the pairing link hands it the token; `%` (escapes, IPv6 zone ids) is refused, and IPv6 hosts are stored as browsers serialise them (`[::ffff:127.0.0.1]` becomes `[::ffff:7f00:1]`). The origin gets CORS on `/api` and `/healthz` only (`Security/CrossOrigin.cs`: preflights answered 204 before the token check, the exact origin echoed, `Vary: Origin`, `Access-Control-Allow-Private-Network: true` when asked, never `Allow-Credentials`; 401s carry the CORS headers too), and its `/ws` upgrades pass the Origin check. The pairing link `{origin}/#engine=http://127.0.0.1:{port}&token={token}` hands that origin the engine URL and token in the fragment. The engine's own origin and the dev origins get no CORS headers.
- `GET /auth/{token}` accepts only the session token (an integration token gets 401, so it can never be exchanged for the session token), and the pairing links carry only the session token. It redirects to `/#token={token}`; the web client reads the fragment (never sent to a server), keeps the token in `localStorage` (per origin, so per port), removes it from the address bar and sends it as a Bearer token. The token is random per start unless `--token` is given.
- **The elevated launches** (`Sensors/Libre/PawnIoInstaller.cs`; spec/docs/api.md "The PawnIO driver"): the engine never runs elevated and never prompts by itself; it starts two things with administrator rights, each only when a session token asks: the sensor helper's `--register`/`--unregister` (next) and PawnIO's installer (`POST /api/sensors/sources/libre/driver`; integration tokens get 403). It runs only `pawnio/PawnIO_setup.exe` beside the engine (`AppContext.BaseDirectory`), only when its SHA-256 is the one pinned in the code (`PawnIoInstaller.BundledSha256`, PawnIO 2.2.0), checked right before each launch with the file held open for reading and shared for reading only until the launch returns (so it can't be written, renamed or deleted, nor a folder on its way renamed, in between), launched by the path that open handle resolves to (`GetFinalPathNameByHandle`, `PawnIoFinalPath`, its `\\?\` dropped only when the rest fits `MAX_PATH` and Windows' normalisation changes nothing in it (no name ending in a dot or a space, `GetFullPath` gives it back as it is), else nothing is launched and the install is `failed`), never the fixed path again, so a junction on the way retargeted after the hash can't swap the file run; a file that is itself a link (a reparse point) is refused; with the fixed arguments `-install -silent`, through the shell with the `runas` verb (the installer's manifest asks for administrator rights itself, so Windows asks once). Nothing in the request names a path or an argument. After an engine crash at any step each file is its previous version or its new one, never a mix, on every platform. After a power loss, on a drive that honours flush requests: on macOS a write that answered survives (the file and every folder get `F_FULLFSYNC`, which empties the drive's cache too; a file system that can't do it gets `fsync`, with one warning per process); on Linux it survives (`fsync` on file and folder); on Windows it survives on NTFS (the rename is `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`, which matters only for a move done as copy and delete; what makes the same-folder rename durable is the folder, opened for writing, getting `FlushFileBuffers` after it). A file system that can't flush folders at all (`EINVAL` or `ENOTSUP` on Unix; `ERROR_INVALID_FUNCTION` or `ERROR_NOT_SUPPORTED` on Windows, or any Windows file system but NTFS, whose folder flush can succeed without reaching the disk) is logged once per process, and there a save that answered can come back as the previous version and a new profile or blob can be missing, but no file is torn; any other flush failure fails the write. The fault tests (`CrashSafetyTests`) prove the order of the steps, not lost drive caches.

## Conventions

- Logging: Serilog (see `LoggingGuidelines.md`). The engine's level is the `logLevel` setting (a `LoggingLevelSwitch`, live); `RecentLog` (`Hosting/`), a sink in the log file's branch, keeps this run's newest 2,000 entries (at most 2 MiB; messages cut at 4,096 characters, exceptions at 8,192, sources at 256), each with a `seq` from 1, for clients (`GET /api/logs`). `CrashLogging` logs unhandled exceptions (`Fatal`, then the log is written out) and unobserved task exceptions (`Error`). Text that can carry the session token goes to the console only (`LogTargets`): the sign-in and pairing links (the file gets them redacted) and a browser launch's error (`BrowserLauncher`; the file gets the error's type), though what it starts names only the redirect file. That the token stays out of ASP.NET's own messages (the request path `/auth/<token>`, the redirect to `/#token=…`) rests on `Program.cs`'s `Microsoft` logging override staying at Warning, which the `logLevel` setting can't lower; `LogLevelPinTests` fails if a code change lowers it, and doing so needs the token redacted before the file and recent sinks first.
- Tests pin culture, time and the PC's regional format (`SceneRuntimeOptions.Locale`: the invariant format in the Core kits, en-US in `EngineFactory`); goldens and other process-wide font state run in the non-parallel `Golden` collection.
- Docs for 2.0 live in `docs/2.0/`. `PLUGINS.md` is 1.x's plugin guide with a section on what 2.0 does differently; `PLUGIN-ARCHITECTURE.md` describes the 2.0 engine's hosts; `PANELS.md` (USB panels, 1.x) lives on `1.4.x`.

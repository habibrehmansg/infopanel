# Video: the preview's H.264 encoders and FFmpeg

- **Preview video** (`InfoPanel/Preview/Video/`): an `h264` subscription's sink has a `VideoStream`. The render thread routes each frame (`Route`: PNG with `fallback` when it is over the video size, 4096 a side and 4096×2304 in all, or the stream has no backend for it) and copies the rest into a one-frame raw slot (the newest wins; the only place a video frame is dropped); one loop task reserves a slot of the ordered output queue (`OutputSlots`, 8, never drops) and submits (2 in the encoder at most); each accepted submission gets exactly one outcome, its slot released in a `finally` unless queued; outcomes must come in order. Generations: leaving video for PNG and a failed session start a new one, and the send side drops older frames. A watchdog aborts a session with no output for 1 s while frames are in it; every retirement (failure, size change, the subscription's end) aborts without draining and waits at most 2 s for the teardown (`Quarantine`; a teardown that never ends is leaked, logged and counted, three give the backend up for the run). Failures (refused frame, error, stall, unknown or out-of-order outcome, an avcC `H264Sps.RewriteForStream` refuses) replace the session; three in 30 s, a faulty start or a bad avcC give the backend up for the stream; none left: PNG with `encoder.failed`. A start the backend calls unsupported (cached per size for the run) or busy (retried from 1 s to 30 s) isn't counted. `H264Backends` is the run's chain, best first, each probed once on a background task: on macOS VideoToolbox called directly (`VideoToolboxH264`: hardware required; its mandatory settings, Baseline, no frame reordering and the BT.709 matrix, set and read back, a refused or wrong one failing the start as a fault; hints logged when refused; its output callback's exception barrier reports a failure when reading a frame throws; teardown on a quarantine thread), on Windows Media Foundation's hardware encoder MFT, whichever the graphics chip provides (`MediaFoundationH264`: one implementation for every vendor, the vendor id read for the log only; a probe once per run walks the hardware entries `MFTEnumEx` lists, in Windows' order, and trusts the first activation that passes a three-frame test encode at 322 × 194, bound to its identity (CLSID, hardware URL, device key, driver version); NV12 converted on the CPU into system-memory samples, no D3D device; COM through .NET's in-box `[GeneratedComInterface]` in `MediaFoundationNative.cs`, the real catalog and port in `MediaFoundationCom.cs`, each raw pointer with one owner and every wrapper released by `FinalRelease`; the backend runs over two seams (`IMfCatalog`, `IMfEncoderPort`), so `MediaFoundationSessionTests` and `MediaFoundationStreamTests` drive it over fakes on any OS, `MediaFoundationAbiTests` pin the declarations against the SDK headers' table and run the real port over synthetic COM objects on any OS, and `MediaFoundationTests` drive the real encoder on Windows (skipped only with `INFOPANEL_NO_HARDWARE_ENCODER=1`; decoded by the first `ffmpeg.exe` on `PATH`, a test tool only)); nothing on Linux. Windows has no software encoder and never builds or looks for ffmpeg (`H264Backends.ChainFor`, the chain per OS: Windows [Media Foundation], macOS [VideoToolbox, ffmpeg], Linux [ffmpeg]). Then, on macOS and Linux, the software encoder: the user's own ffmpeg as a child process (`FfmpegH264`, never shipped: found by `FfmpegDiscovery`, `--ffmpeg`, else the first executable on `PATH` (fully qualified folders only), else `/opt/homebrew/bin` and `/usr/local/bin`; probed by a 64 × 64 encode of two frames with the production arguments, which must give an encoded keyframe and an avcC `RewriteForStream` takes within 5 s, its processes killed after and its session torn down within the quarantine bound (a teardown past it fails the probe and counts as a quarantined session, `Quarantine.Abandon`), and logged with its version and path; the engine's stop cancels a probe still running and ends every live stream (`H264Backends` tracks them, so a socket closing after the engine exits leaves nothing running), and waits, within `H264Backends.StopBound`, for them to kill and collect their processes, then kills every process the backend started that still runs (it owns each until it exits, a quarantined or abandoned session's included) and collects it within `H264Backends.ReapBound` (`IH264Backend.ReapAsync`): `H264Shutdown`), libx264 Baseline, `-tune zerolatency`, 8 Mbit/s, the BT.709 matrix into limited range with the colour set on the frames (`setparams`), fixed arguments through `ArgumentList`, no shell; raw RGBA in on its input from a writer task (a submission never waits for the write), FLV out, its error output (and the probe's `-version` output) read to the end in bounded chunks (`BoundedOutput`: the first 20 error lines logged, each cut at 1,024 characters; the rest dropped), each access unit the outcome of the oldest frame outstanding with its timestamp checked; its arguments are fixed, so a keyframe request (once its session's keyframe is out) or a new frame rate retires the session and starts another (`ChangesLive` false; not a failure), and its abort cancels the blocked write and both readers' reads and kills the process (alone, SIGKILL: ffmpeg starts none, and a tree kill stops the process first, which an exiting engine could leave stopped), the teardown ending once they have (a teardown past the bound gives ffmpeg up for the stream instead of starting another beside it: `GivesUpWhenTeardownHangs`). Test engines have a fake (`FakeH264Backend`), so video runs on any machine, `VideoToolboxTests` drive the real one (skipped only with `INFOPANEL_NO_HARDWARE_ENCODER=1`; decoded by Homebrew's ffmpeg), and `FfmpegH264Tests` and `FfmpegDiscoveryTests` drive Homebrew's ffmpeg and stand-in scripts (skipped, saying why, without ffmpeg, and on Windows, which has no software H.264 encoder). Keyframes carry the avcC rewritten to say "no reordering" (Baseline only), its codec string and `encoder`. The socket's send loop checks the close first, sends at most 8 errors and 4 frames a turn, and leaves a wake pending when more wait. `RenderService.Refresh` asks the render loop for a fresh frame (a keyframe on a still panel).

- **Video** (`InfoPanel.Core/Images/Video/`, spec/docs/smart-nodes.md "Video files"): FFmpeg's libavutil 61, libavcodec 63, libavformat 63 and libswscale 10 through the engine's own function-pointer binding (`FFmpeg`, struct offsets pinned in `FFmpegAbi` from `native/ffmpeg/offsets.c`; no package), loaded by full path beside the engine, else from `INFOPANEL_FFMPEG_DIR` (development: Homebrew's `/opt/homebrew/lib`; a test engine's `Engine:FFmpegDir` setting replaces both, and `EngineFactory` points it at an empty folder). Loaded, the engine lists `media.video`; otherwise it logs once and a video item is unsupported, kept. `VideoProbe` (`Spec/`) reads a container's headers before FFmpeg sees a byte; `VideoPlayer` (inside `MediaSampleCache`, frames in its budget) runs up to 8 decode sessions (video × decode size × playback × owner: a simulated loop's are its own, which a live video closes at once to make room and which never close a live one) within an estimated 768 MiB of decoder memory (`WorkingSet`), each on its own thread a few frames ahead of the tick clock, or synchronously to the exact frame for one-off renders and tests; FFmpeg reads only through custom I/O over `BlobStore.OpenVerified`, and a closed session's decoder stops at FFmpeg's next read. The video tests (`VideoProbeTests`, `VideoDecoderTests`, `VideoSessionTests`, `SceneVideoTests`, the `video-media*` goldens (within 6 levels a channel: another FFmpeg may convert a few levels apart), `VideoPreviewTests`) use `InfoPanel.Core.Tests/Fixtures/video/` (made by `native/ffmpeg/make-fixtures.sh`, only on purpose) and skip, saying why, without the libraries. The downloads carry no FFmpeg (the engine loads the libraries beside it or from `INFOPANEL_FFMPEG_DIR`); `native/ffmpeg/build.sh` is the pinned decode-only build kept for a future bundle, which would then need its licence text shipped as libusb's is (terms: LICENSES.md). The same libraries give the `rtsp` provider (spec/docs/providers.md): its tests (`RtspProviderTests`) run a minimal RTSP camera on loopback (`Images/RtspTestServer`, the H.264 fixture's frames as RTP over TCP; hostile answers, FU-A floods, a switch to a larger picture or alternating pictures, a slow first frame, a track described as H.265, and a camera that checks its address and Digest (MD5, SHA-256, beside other challenges, in headers of their own or in one) on demand) and skip, saying why, without the libraries.

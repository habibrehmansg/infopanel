# The engine's command line

`--fresh` is a dev and test flag that wipes the whole data folder before start-up: it needs `--data-dir`; it refuses a filesystem root, the home folder or a folder above it (checked on the path as given and on its real path, links resolved) and a folder with any top-level entry the engine doesn't write (`store.json`, `profiles.json`, `tokens.json`, `pairings.json`, `settings.json`, `service-credential`, `service-credential.bin`, `profiles/`, `blobs/`, `fonts/`, `logs/`, `plugins/`, `plugin-settings/`, `plugin-state.json`, `devices.json`, `runtime.json`, `engine.lock`, step-1's `profiles.xml` and `assets/`, the 1.x migration's `import-v1.json`, their write temp files); otherwise it deletes everything in the folder except `engine.lock`, including whatever is inside those engine folders (user-added fonts too), removing links without following them. The web root is `--web-root <dir>` as given, else `{BaseDirectory}/wwwroot` when it has an `index.html`; with neither the engine serves the API and `/ws`, and a plain-text "no web client installed" page on unmatched non-file paths outside `/api`, `/ws` and `/auth` (file-like paths such as `/index.html` or `/missing.js` return 404). `--mock` is mock mode: the mock sensors instead of the platform's real ones, and simulated values for well-formed keys no source handles; without it unknown keys are `unavailable` (the `dev` launch profile and every test host pass it). Exit codes: 0 clean, 1 fatal (a data folder whose marker this engine can't honour included), 2 bad arguments (a bad built-in web client origin included), 3 data folder in use: a **second launch** (no `--no-browser`) first asks the engine that holds the folder, over its local channel as a `launch` companion, to open the editor, and prints "InfoPanel is already running; opened the editor" (`Hosting/SecondLaunch.cs`); when nothing answers on the channel (an engine stopping closes it before it lets go of the folder, which it keeps through its clean-up), any launch waits for the folder up to 5 s (`SecondLaunch.HandOff`) and starts once it is free. An `infopanel:` link (docs/2.0/desktop-shell.md, "Opening the editor") is accepted only as the only argument, any case, and never read (`EngineOptions.FromLink`): on a held folder a second launch; an engine it starts opens the editor once it listens; with anything else it is an unknown argument, exit 2. On macOS the bundle declares the scheme and the app delegate, set before the AppKit loop runs, answers `application:openURLs:` as opening the app again; the Windows installer registers it per machine. The sign-in link (`/auth/<token>`, printed only when a web client is served here, since it leads nowhere otherwise) and each `--allow-origin`'s pairing link go to the console only (the file log and the recent entries get them with `<token>`). `--allow-origin`'s default is the origin a release build carries (the MSBuild property `InfoPanelAllowOrigin`, recorded as the assembly metadata `InfoPanel.AllowOrigin` by `InfoPanel/WebClientOrigin.targets`; none in a build from source), checked as the flag is; any `--allow-origin` replaces it.

**On Windows the engine is a Windows-subsystem program**, so it opens no console window: `InfoPanel/InfoPanel.csproj` sets `OutputType` `WinExe` for a Windows runtime (`$(RuntimeIdentifier)` `win-*`, as every Windows publish has, on whatever computer it is built; `WindowsSubsystemTests` reads it per runtime, `EnginePublishTests` pins `InfoPanel.exe`'s PE subsystem at 2). A build for no runtime, and every macOS and Linux build, stays the console program (`Exe`) the Web SDK makes. A shortcut, the installer's finish page, the Run value or an `infopanel:` link starts it with no console, so no console window's close ends it; its plugin and panel hosts (`--plugin-host`, `--panel-host`, the same executable) show none either. The command line keeps its output: first thing in `Program.cs`, after the hosts' modes return and before anything touches `Console`, `Hosting/ParentConsole.AttachIfNeeded` runs the rule: only on Windows, only when standard output or standard error can't be written to (each output stream is asked itself, as the .NET runtime asks it before giving `Console.Out` a real stream: not 0, not -1, and a `WriteFile` of zero bytes to it succeeds; so a pipe, a file and `NUL` count, and a stale value a parent can hand a Windows-subsystem child, a read-only handle or the parent's own console handles, which take no write before the attach, don't; standard input is judged apart, by `GetFileType` knowing its type, and is never a reason to attach; a parent that sent both output streams somewhere writable, as the tests, the release workflow's smoke run and the engine's hosts do, is left exactly as it is: the two zero-byte writes are all that happens: they write no data, though a message-mode named pipe's reader sees one empty message a stream, as .NET's own console set-up also sends), every unusable slot of the three cleared to 0 whatever its value, -1 included (never closed: it isn't the engine's; Windows' attach fills only a slot that holds 0), `AttachConsole(ATTACH_PARENT_PROCESS)`, and nothing else; a stream the parent sent to a usable handle is put back as it was after the attach, and a cleared slot keeps the console's. So a start from `cmd` or PowerShell prints `--help`, argument errors, "already running; opened the editor", the console log and the sign-in and pairing links in that terminal; a start with no terminal (a double-click) attaches nothing and makes no console (`AllocConsole` is never called, `WindowsSubsystemTests.TheEngine_NeverAllocatesAConsole`), and its console lines go nowhere without failing (the log's lines are in the log file too, the links redacted). **The limit:** a terminal doesn't wait for a Windows-subsystem program. Typed at an interactive Command Prompt or as `& InfoPanel.exe` in PowerShell, the prompt comes back at once, the engine's lines arrive after it, and `%ERRORLEVEL%` or `$LASTEXITCODE` isn't the engine's exit code (PowerShell sets none). To wait for it and get the code: `start /wait InfoPanel.exe …` (then `%ERRORLEVEL%`), `cmd /c` or a batch file (both wait), `Start-Process InfoPanel.exe -ArgumentList … -NoNewWindow -Wait -PassThru` (its `ExitCode`), or a redirect or a pipe (`InfoPanel.exe --help > help.txt` in `cmd`; `InfoPanel.exe --help | Out-String` in PowerShell, whose `>` neither waits nor redirects for such a program). Attached, the engine shares that terminal's console as a console program does: Ctrl+C there stops it, and closing the terminal ends it.

# Storage, settings and the data folder

- **Storage and editing**: `InfoPanel.Documents.Workspace` (Core) is started once (`Workspace.Start`): the data folder's marker checked, both stores opened, the blobs swept, then the first change: on a first run (the store didn't exist), unless 1.x data waits to be migrated (the 1.x folder has data and the data folder no `import-v1.json`: `WorkspaceOptions.ExamplesWanted`), the example for the platform and sensor source (`Workspace.FirstRunExamples`: "Mac overview", 800×480, on macOS with the Mac's own sensors; "Wide bar" with `--mock`, whose sensors it shows, and elsewhere), the blobs it names stored first as an upload stores them (hash checked; an example one of whose blobs can't be stored is skipped and logged). It lists the store's profiles with their status, opens a document the first time anything reads it and keeps it open until it is deleted or the engine stops (then disposed), and checks create and duplicate bodies. A profile's id is its folder's name: a stored document with another `id` is opened under the folder's and saved with it. A profile that isn't `ok` is checked once per run and never rewritten. Each `ProfileDocument` (`Documents/`) applies commits, undo, redo and revert as in `spec/docs/commit.md` (one transaction under its lock; field revisions; coalescing keys: `gesture:` always merges, other keys within 1 s; per-document and process-wide history caps), with exact dirty; save writes the current generation to its `document.json`. Unsaved changes survive a restart (`docs/2.0/data-folder.md`, "Unsaved changes"): `RecoveryScheduler` (one per workspace, one timer and one run at a time, off every request path) keeps each dirty document in `profiles/{id}/recovery.json` (`RecoveryFile`: the canonical document, the saved bytes' SHA-256 as `base`, `written`) 2 s after its last change and at most 10 s after its first not yet kept, through `ProfileDocument.Checkpoint` under the save lock (so serialised with Save and disposal; the store writes only while the profile is listed), and `Workspace.Dispose` keeps every one not yet kept at an orderly stop; a change that leaves the document clean removes the file before it answers, and Save rewrites it against the new save or removes it after `document.json`. At open a usable file whose `base` is the saved bytes is applied as one undoable step (`ProfileDocument.Restore`: revision 2, dirty, `recovered` until a save or revert); one that can't be used is logged and left.
- **Settings** (`InfoPanel.Core/Settings/`): `SettingsStore`, opened at start-up after the workspace, keeps the engine settings in `settings.json`: `format` (`infopanel.settings/1`) and only the members someone set, each absent one at its default (1.4.x's: `frameRate` 15 (1–60), `graphRate` 1000 ms (100–3000), `logLevel` `information`, `sources.libre` on, storage on, `storageInterval` 30 s (1–300); `sources.network.publicIp` on (whether the network source looks up the public address; not a 1.4.x setting); `sources.weather` `enabled` on, `units` `auto` (`metric`, `imperial`), `place` null (1–200 UTF-16 code units, not all white space; null: the place the service finds for the request's network address); `media.localNetwork` on (whether media providers may connect to this computer and the local network; a change drops what the providers fetched, so each web image is fetched again under the new rule); `clients.{name}`, a client's own preferences, at most `settingsClients` (16) of `settingsClientBytes` (64 KiB) each, measured on their canonical form). The limits are the format's settings limits (`SpecLimits`, spec/docs/limits.md), each refusal with its `limit.*` code. `Apply` merges a change (`null` removes a member), refuses unknown members and out-of-range values with every error at its path (`CheckChange`, which the examples' `settingsChange` rules run too), writes at once with `AtomicFile` and raises `Changed` with a run-local `version`; a change that leaves the content as it is writes nothing. Unknown members in the file are kept at any depth; a stored known member that breaks its rule gets its default with a warning. A file that can't be read (over `settingsBytes`, 1 MiB; nested deeper than `settingsDepth`, 64; not JSON; no `format`) or of another major version leaves the defaults in effect, is logged and is never rewritten in that run: every change is refused. The 1.x settings reader clamps the rates and interval to these ranges with an `import.setting` warning. Live consumers: desktop windows ask for `frameRate` (the `/ws` preview keeps its own `maxFps`, 30 when absent), and `SensorHistory` samples every `graphRate` ms (re-timed on a change, samples kept); the engine's logger follows `logLevel`; the network source follows `sources.network.publicIp` (`NetworkSource.FollowSettings`) and the weather source `sources.weather` (`WeatherSource.FollowSettings`), both wired by `AddBuiltInSources` from the store in the services.

`{LocalApplicationData}/InfoPanel/v2`: `~/Library/Application Support/InfoPanel/v2` on macOS, `%LOCALAPPDATA%\InfoPanel\v2` on Windows (`--data-dir` overrides). Layout and rules: `docs/2.0/data-folder.md`. `store.json` is the folder's marker, `{"format":"infopanel.store/1","requires":[]}` (`Persistence/StoreMarker.cs`), written when absent: `Program` reads it, read only, before it creates anything in the folder (`StoreMarker.Preflight`, so a refused start leaves no `engine.lock` either; skipped with `--fresh`, which wipes it), again right after taking `engine.lock` (and after `--fresh`), before anything repairs, sweeps or writes there (the log folder included), and `Workspace.Start` again before the stores open; an unreadable marker, another major version or a `requires` capability the engine lacks (`StoreMarker.Capabilities`, none in 1.0) stops start-up with exit 1 and a message naming it, nothing in the folder changed and a lock file already there left in place. A later engine that keeps blob references outside the profiles' folders, or a rule an earlier engine must enforce, adds a store capability there. The 2.0 store: `profiles.json` (display order only, within its own bound `profileListBytes`: a create or duplicate past it is 422 `limit.profileListBytes`, and a larger file isn't read), `profiles/{id}/document.json` (each profile's saved document, `id` a lower-case UUID; the blob sweep's root rule: every file under each folder of `profiles/` at any depth, read through links (each real folder once), but OS metadata (`.DS_Store`, `._*`, `Thumbs.db`, `desktop.ini`) and write leftovers (`*.{32 hex}.tmp`), plus each folder's `document.json`; each is scanned as text for `sha256:` ids, as written and with JSON escapes decoded, JSON or not (a `document.json` must be JSON too), and one that can't be read, isn't a regular file, or a link whose roots can't be read stops that run's deletions, so what a later engine keeps there keeps its blobs), `profiles/{id}/recovery.json` (unsaved changes kept across a restart, data-folder.md "Unsaved changes": a sweep root by the rule above, its `recovery.json.{32 hex}.tmp` leftovers removed at start-up), `profiles/{id}/versions/{n}.json` (earlier saves, data-folder.md "Earlier saves": each save that changes the bytes first writes the document it replaces there, byte for byte, numbered after the highest present (any letter case, any type), through `AtomicFile` (the file and `versions/` flushed; the folders above only for a profile's first version in a run or after their flush failed) before `document.json` is replaced, or reuses the newest when it holds those bytes (a retried save; its content flushed on the handle compared with the store's checked native flush, `EINVAL` and `ENOTSUP` included, a new version kept when that fails), then, after every save that wrote the document, drops the oldest past 10 or 64 MiB, the newest always kept; only exact names (`^[1-9][0-9]{0,18}\.json$`, regular files checked on an open handle, not links) count, their `{n}.json.{32 hex}.tmp` leftovers are removed at start-up, a `versions` that is a link or a file is never followed or written, and a version that can't be kept or dropped is logged while the save goes on; sweep roots by the rule above; restore by hand: with the engine stopped, copy a version over `document.json`; the sweep flushes `profiles/`, every profile's folder and `versions/` before it deletes a blob, and deletes nothing when that fails), `blobs/{64 hex}` (media and other blobs by SHA-256; a blob's file is hashed on its first read in a run, the verdict cached per file length and last-write time (at most 4096 verdicts, the least recently used dropped first), a profile export hashes every blob it archives, and a file that doesn't hash to its id counts as not stored until the right bytes are uploaded again); and `fonts/` (user fonts; Inter is bundled), `logs/infopanel-{yyyyMMdd}.log` (`Hosting/EngineLogFile`: 100 MiB a file, the newest 7 kept; a target that isn't a regular file turns the file log off for the run, with one console warning), `runtime.json` (pid, port and URL while running: a hint, since a crash leaves it; liveness is the lock and `GET /api/session`), `tokens.json` (integration tokens, hashes only, 0600), `pairings.json` (paired clients with their secrets, and the last port; 0600, on Windows a user-only access list), `settings.json` (the engine settings, only those set; `infopanel.settings/1`), `devices.json` (the USB panels the engine has seen and their settings, `infopanel.devices/1`, docs/2.0/panels.md: written atomically; one it can't hold whole is never rewritten and panels are off for the run), `engine.lock`, `import-v1.json` (the 1.x migration's run-once record), `service-credential` (macOS, Linux; 0600) or `service-credential.bin` (Windows; DPAPI for this user, a user-only access list): the credential a client provides for the configured service, with its address and rejection, only while one is kept (its temp files removed when the store opens).

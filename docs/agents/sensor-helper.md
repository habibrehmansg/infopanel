# The elevated launches and the sensor helper's task

- (The elevated launches: the first sentence is in `CLAUDE.md`'s Security model.) It runs only `pawnio/PawnIO_setup.exe` beside the engine (`AppContext.BaseDirectory`), only when its SHA-256 is the one pinned in the code (`PawnIoInstaller.BundledSha256`, PawnIO 2.2.0), checked right before each launch with the file held open for reading and shared for reading only until the launch returns (so it can't be written, renamed or deleted, nor a folder on its way renamed, in between), launched by the path that open handle resolves to (`GetFinalPathNameByHandle`, `PawnIoFinalPath`, its `\\?\` dropped only when the rest fits `MAX_PATH` and Windows' normalisation changes nothing in it (no name ending in a dot or a space, `GetFullPath` gives it back as it is), else nothing is launched and the install is `failed`), never the fixed path again, so a junction on the way retargeted after the hash can't swap the file run; a file that is itself a link (a reparse point) is refused; with the fixed arguments `-install -silent`, through the shell with the `runas` verb (the installer's manifest asks for administrator rights itself, so Windows asks once). Nothing in the request names a path or an argument. One at a time (409 meanwhile), however long the installer runs: waited for until it ends, never killed, its outcome whenever it comes (the engine stopping abandons the wait: after `Dispose` no outcome is published and nothing called back, even when a launch blocked then returns); exit 0 starts a new sensor helper, and the driver stays `installing`, another install refused, until the engine has read the driver again and that helper has said hello, or none will (Libre off, the source stopped, its start failed: then the registry's state at once), counted by the sampler (`LibreSampler.DriverSettling`) and read after the installer's own flag (`PawnIoInstaller.Report`, `Start(busy)` under its lock). A missing file, a link, another hash, a replay or another operating system means no installer (409, `installer: null`); another hash is logged once. The engine never uninstalls PawnIO. **The installer isn't in the repository**: a Windows package (and a try folder) puts PawnIO 2.2.0's `PawnIO_setup.exe` from its GitHub release (namazso/PawnIO, 3,410,960 bytes, signed by namazso, SHA-256 `1f519a22e47187f70a1379a48ca604981c4fcf694f4e65b734aaa74a9fba3032`) at `pawnio/PawnIO_setup.exe` beside the engine; a build carries none, so it offers no install. Bumping PawnIO changes `BundledVersion` and `BundledSha256` together.
- **Reading all sensors: the sensor helper's task, run as SYSTEM** (`SensorHelper/HelperTask.cs`, `HelperTaskCommands.cs`, `HelperTaskWindows.cs`; `Sensors/Libre/LibreElevation.cs`, `LibreHelperChooser.cs`; spec/docs/api.md "Reading all sensors"). Unelevated, LibreHardwareMonitor reads fewer sensors even with PawnIO. `POST /api/sensors/sources/libre/elevation` (session only; `DELETE` removes it) runs this install's own helper, checked as the PawnIO installer is (held open shared for reading until the launch returns, never a link, by its handle's final path; one at a time, never killed), with `--register --user <the engine's user SID>` (`--unregister` for `DELETE`), through Windows' command processor run with `runas` (`LibreElevation.CommandProcessorArguments`): an elevated process doesn't take the engine's environment but the one Windows builds for the user who approves it, with that user's `HKCU\Environment`, which their own programs write, and .NET's host and runtime act on `DOTNET_*`, `COMPlus_*`, `CORECLR_*` (a profiler's DLL), `COREHOST_*` (a trace file) before `Main`, where the helper can't refuse them; `cmd.exe` (no .NET program; `/d`, no AutoRun) lists the variables with those prefixes and `COR_*` into a file in the helper's folder (under Program Files), clears them reading that file in its own process (a `for /f` over a command would start another `cmd.exe`, with AutoRun), checks none is left (a name with a line break escapes the listing; else exit 15, the helper not run; every query is `(set X)`, since SET matches the spaces after a prefix too) and runs the helper by its final path (a path with `"`, `%` or a control character is `notInstalled`); and only when that final path is under Program Files (`FOLDERID_ProgramFiles` from the known-folder API, never an environment variable); anywhere else the state is `unavailable` · `notInstalled` and nothing is launched. `--register`, elevated, refuses (exit codes in `HelperTask`) when it isn't elevated, when its own final path isn't under Program Files, for a SID that isn't a user's (`LookupAccountSid`), or when that final path can't be the task's action as it is (exit 16: Windows' normalisation would change it, as `PawnIoInstaller` checks, or it holds a Task Scheduler substitution, `$(`, which the user's own runs could fill in); it creates or updates that user's task in one call (`TASK_CREATE_OR_UPDATE`, never deleted first, so a refusal keeps the task there): `\InfoPanel 2\Sensor helper <SID>` (not 1.x's `\InfoPanel`: 1.4.x's Run on startup is a root task of that name, and a task and a folder of one name can't both be there), registered through the Task Scheduler's COM object (late-bound) with its definition in memory, never from a file. Every time, it first sets the `\InfoPanel 2` folder's security descriptor (`HelperTask.FolderSecurityDescriptor`: owned by Administrators, protected from the root's, which lets any user create a task there; SYSTEM and Administrators full control, inherited, without which an administrator can't update a task a user made there first; authenticated users read), and it sets the task's own, owner and all, both before an update and after registering (an update keeps the existing one: a task a user made at that path first would stay theirs, shown on a PC, and its owner could replace it between the update and the security set after; a task there that can't be made the administrators' first isn't updated, exit 17); then it reads the task back and fails (exit 17) unless it runs as SYSTEM with one action, this helper with `--serve --user <SID>`. `--unregister` removes the folder once no task is left in it. The task runs as SYSTEM, never under the user's token: a task under the user's token with the highest run level builds its environment from `HKCU\Environment`, which any program of the user writes, and .NET honours `DOTNET_STARTUP_HOOKS`, `DOTNET_ROOT`, `DOTNET_ADDITIONAL_DEPS` and the profiler variables before `Main`, so any user process could have run code with administrator rights without a prompt (shown on a PC). SYSTEM's environment isn't the user's, and it covers standard users too. No trigger; on demand only, `IgnoreNew`, no time limit, kept on battery, normal priority; its security descriptor is owned by Administrators and gives Administrators and SYSTEM full control and the user read and run only (their unelevated engine starts it with `schtasks /Run`). `--serve --user <SID>` creates the pipe `ipsensors-<SID>` first-instance, owned by SYSTEM, its protected DACL granting SYSTEM and that user only and denying network logons; a client whose user (its token, read at identification level: `ImpersonateNamedPipeClient`, `OpenThreadToken` as the helper, reverted on every path, the token read after; nothing else works as an identification-level client, .NET's `RunAsClient` included, which refused every engine on a PC) isn't the SID, or whose token is below medium integrity (a sandboxed process of the user's may open it for reading), is dropped unserved; one whose user can't be told is dropped and the helper ends (only the user's processes can open the pipe, so that was its engine, which falls back; waiting on would hold the task's one instance against its next start); the client accepted has 5 s to say hello; it serves one engine and ends when that engine disconnects, or after 30 s with none. The engine, unelevated, starts the task when it exists and runs this install's helper with those arguments (read through the Task Scheduler), opens the pipe without `CurrentUserOnly`, and checks the pipe's owner is SYSTEM (`GetSecurityInfo` on the handle; it can't open a SYSTEM process to read its image path) before it sends anything: a squatter, a process of the user's own, can't create a pipe SYSTEM owns. A start with no pipe within a second is made again (`IgnoreNew` drops one while the helper it replaces still ends); the task's helper is the one only once it answered the engine's hello. A wrong owner, a refused start, a helper that drops the engine before that answer, or 10 s without a pipe falls back to the engine's own child, logged with why and reported as Libre's `elevation.fallback` while `on`; so does the start after two task's helpers in a row were lost before answering a sample, each given up as failed (it ended or dropped the engine, stopped answering, failed its reads or its start; `ILibreHelper.GivenUp`), while one the engine stopped on purpose (Libre off, a restart it asked for) neither counts nor resets the count (the start after that tries the task again). An elevated engine keeps its own (elevated) child and offers nothing (`engineElevated`). The helper is a Windows-subsystem program (no console window from a task) with `StartupHookSupport` off (its runtimeconfig is in Program Files). **Limits:** Windows' prompt names its command processor, not the helper; anything else the approving user's own programs wrote for their elevated processes (their other variables, their registry) still reaches that one consented `cmd.exe` and the helper it runs, as it reaches any program that user elevates; session 0's readings of a discrete GPU aren't checked yet.

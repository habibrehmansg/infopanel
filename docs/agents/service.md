# The configured service and pairing through it

- **The configured service** (`InfoPanel.Core/Service/`; `Api/ServiceEndpoints.cs`; spec/docs/api.md "The configured service"): the engine keeps a credential a client provides for one configured service. The address is the `service.address` setting (an origin: `https`, or `http` on a loopback host; `ServiceAddress`), else the build's web client origin (`EngineOptions.DefaultServiceAddress`, from `InfoPanel.AllowOrigin` whatever `--allow-origin` says; none in a build from source, so no service until one is set). `GET /api/service` (state, `store`, and a fingerprint of the stored credential: the first 16 hex of its SHA-256), `PUT` and `DELETE /api/service/credential`, session only (integration tokens 403); a credential is an RFC 6750 token of at most 4,096 characters (the schema's pattern, which refuses a trailing line break too, and `ServiceCredentials.IsWellFormed` agree), and no 422 echoes it. `ServiceCredentials` keeps it in one store (`FileServiceCredentialStore`): `{data}/service-credential` through `AtomicFile.WritePrivate` (0600) on macOS and Linux, `store: "private"`; `{data}/service-credential.bin` on Windows, encrypted with DPAPI for the current user (`CryptProtectData` with `CRYPTPROTECT_UI_FORBIDDEN`, hand-written `LibraryImport`) through a temp file from `IWindowsSecurity.CreateFile`, `store: "protected"`. No Keychain store: an unsigned or ad-hoc-signed binary's Keychain access binds to its code hash, so every update would prompt; the contract's `store` keeps `keychain` for a later signed build. The record holds the address it was given for and whether the service refused it: a change of the address in effect removes it, a settings change before it is stored (`SettingsStore.Changing` asks `ServiceCredentials.AddressChanging`, which holds its lock until the change is in effect; a store that can't remove it, or a record it couldn't remove earlier, refuses the change with 503 `storeUnavailable`, so no record outlives its address), one made while the engine was stopped (a build's default included) at start; a write or removal that reached the file but not its folder's flush is in effect, as on disk, and the next one flushes; never in `settings.json`, the log, `RecentLog` or an answer. A `PUT` that replaces a `present` credential for the same address with other text then asks the service, once and in the background, to forget the replaced one (`ServiceRelease`, started after `Put` answers it, never awaited: `DELETE /svc/v1/device` with it as the Bearer token through `ServiceClient.SendWithAsync`, pending until it ends and dropped, its request cancelled if still being made, when the credential is provided again, the address changes or the engine stops (`ServiceCredentials.MaySend` checks under the store's lock right before sending; `ApplicationStopping`, and the host's disposal waits at most 2 s, after which one still running starts no request and logs nothing; pending ones are tracked by instance, so one ending never clears a later one of the same text); 15 s, one attempt by the engine (the connection layer may resend within it), nothing stored; whatever the answer, nothing changes and a 401 rejects nothing; one log line, never a credential).

- **Pairing through the configured service** (spec/docs/api.md "Pairing through the configured service"; `Security/PairingPasses.cs`, `InfoPanel.Core/Service/PairingKeys.cs`, `Api/PairingEndpoints.ExchangePassAsync`): the `service.pairing` setting (off by default; only `PATCH /api/settings`, so only the session token) lets `POST /auth/pairing/pass` (no token; CORS as `/api`, `CrossOrigin.AppliesTo`) exchange a pass the configured service signed for the run's token and a pairing, answered exactly as a code's first use (`pairings.Create`, `replaces`, no pairing when the file can't be kept). No connection: the engine only fetches the service's public keys. `PairingPasses.CheckAsync` checks in order, the first failure 403 `pairingPassProblem` with one word: the switch read at the request (`off`, before the body is read) and again before the nonce is taken; the compact form (three unpadded base64url parts, the header exactly `{"alg":"ES256","kid","typ":"infopanel-pairing-pass"}`, a 64-byte r‖s signature; a header whose text doesn't decode, a lone surrogate or bytes that aren't UTF-8, too: `malformed`); the ES256 signature over the first two parts as sent against `PairingKeys.FindAsync(address, kid)`, the address read with the credential's generation (`ServiceCredentials.Binding`) as the check begins (.NET `ECDsa`, a new instance per check: `signature`); the payload exactly `v` 1, `aud`, `device`, `host`, `nonce` (22–86 base64url), `exp` an integer at most 90 s ahead, its text decoding (`malformed`); `aud` `infopanel-pairing` (`audience`); `exp` + 30 s not past (`expired`); `host` the request's `Host` (port aside, any case, as received) and one of `proxy.hosts` (`host`); `device` equal to `ServiceCredentials.Id`, and `Binding` unchanged since the keys were looked up, so one exchange checks against one service (`device`); the nonce new (`PairingNonces`, remembered until `exp` + 30 s, at most 1,024, full refuses, and so does a nonce whose time is no later than one forgotten: `replayed`). The time these checks use never goes back (`PairingPasses.Now`, the latest clock reading seen), so a clock moved back reopens no pass; a clock moved forward and back makes every pass `expired` until it catches up, or the engine restarts. The credential's id is given beside it at `PUT /api/service/credential` (`id`, optional, 1–64 of `[A-Za-z0-9_-]`, `ServiceCredentials.IsWellFormedId`, checked again for the `$` line break), kept in the stored record (`StoredServiceCredential.Id`, `"id"`), replaced or removed with it, read only while the credential is `present` for the address in effect. `PairingKeys`: `GET {address}/svc/v1/pairing-keys` without a credential through `ServiceClient.NewHandler()` and `ServiceClient.Target` (origin only, `https` or loopback `http`, loopback only with `--offline`, no redirect, no proxy, no cookies), 5 s and 64 KiB, `{keys:[{kid,kty:"EC",crv:"P-256",x,y}]}` (other entries ignored, a point off the curve too, at most 16), kept as `ECParameters` by `kid`; fetched for an unknown `kid` or a list an hour old, at most once a minute (a failed or abandoned fetch counts; the fetch isn't the request's, so a client going away doesn't waste it), one at a time; each fetch replaces the list, a failed one keeps it, but a list an hour old answers no key until a fetch succeeds (so a revoked key stops pairing within the hour, the service reachable or not); a change of address forgets it, and a lookup for an address no longer in effect answers none. Logged: "A pairing pass was accepted", refusals as a warning with the word at most once a minute with a count, a list it couldn't fetch with the reason; never the pass, its parts or its nonce (`PairingPassTests` scans the log files, `RecentLog` and `/api/logs`). Accepted: whoever holds a valid pass and reaches a `proxy.hosts` name pairs while the switch is on; a restart forgets the nonces (a pass used just before one could be used again within its time).

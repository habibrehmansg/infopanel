# Plugins

The engine runs plugins built with the `InfoPanel.Plugins` SDK (net10.0), 1.x plugins as they are (built for net8.0 against 1.x's SDK, which 2.0's keeps), and reads their sensors, texts, tables and pictures into the sensor hub as the `plugins` source, under 1.x's keys, so a 1.x profile bound to a plugin reads it live. This page says how the engine finds plugins, runs them, and what it takes from them. Writing a plugin: [PLUGINS.md](../../PLUGINS.md); how hosts work inside: [PLUGIN-ARCHITECTURE.md](../../PLUGIN-ARCHITECTURE.md).

## Packages and where they are

A plugin package is a folder `InfoPanel.{Name}` (letters, digits, `-` and `_`) holding `InfoPanel.{Name}.dll` and, optionally, `PluginInfo.ini` ([below](#plugininfoini)). The engine looks in two folders when it starts:

| Folder | What |
|---|---|
| `{engine folder}/plugins/` | The bundled plugins (none today; the folder stays for first-party plugins), read-only; `--bundled-plugins <dir>` names another folder |
| `{data}/plugins/` | Plugins the user added (per user, in the [data folder](data-folder.md)) |

Folder names are compared ignoring case, and a bundled package wins over an installed one of the same name. A folder whose name isn't `InfoPanel.{Name}`, or that has no `InfoPanel.{Name}.dll`, is skipped with a warning; a folder starting with `.` is skipped silently. In the data folder, a package folder that is a link isn't followed, and the folder's listing is bounded (10,000 entries). A package that can't be read, or a plugins folder that can't be listed, is skipped with a warning, and the other packages start. `--no-plugins` starts no plugin at all.

### PluginInfo.ini

The engine reads a package's `PluginInfo.ini` itself when it finds the package: a regular file, not a link, of at most 64 KiB, UTF-8 with or without a BOM. From its `[PluginInfo]` section it takes `Name` (else the folder's name), `Description`, `Author`, `Version`, `Website` (only an `http` or `https` URL; anything else is left out), `Platforms` and `Access`. Values are cut at 256 characters, the description at 4,096. A file that is missing, a link, too large or unreadable leaves the folder's name and nothing else, with one log line.

`Access` is the one key written once a line, up to 8 times: what the package's plugins read or change beyond their own folder, in plain words ("Reads usage numbers from the app's logs, never message text"). The engine keeps the lines in their order, each cut at 256 characters, empty ones left out and those past the eighth dropped, and lists them with the package (`access`, absent when none); a client shows them with it. They are declared, not enforced.

`Platforms` names the operating systems the package runs on, comma-separated, ignoring case: `windows`, `macos`, `linux`. Without it, or empty, the package runs anywhere. A package whose `Platforms` doesn't name this operating system is `unsupported`: its host never starts, and it can't be turned on or reloaded. A plugin built on a Windows-only library says `Platforms=windows`.

## On, off and reload

Every package is on until the user turns it off. The user's "off" is kept in the data folder's `plugin-state.json` ([data folder](data-folder.md)), by folder name, ignoring case, and a package that is off isn't started at the next start. Only the user's choice is written: a host that crashes, is given up on, or is refused (a duplicate plugin id, `unsupported`) never turns its package off, as 1.x's `plugins.bin` did. A name with no package is kept. The choice is written before the host is stopped or started, so a write that fails changes nothing; a file the engine can't hold whole when it starts (not its format, over 1 MiB, a link, not JSON) is never rewritten: every package runs, and turning one on or off is refused for that run.

Turning a package off stops its host (5 s to shut down, then killed); turning it on starts it, a failed one afresh. Reloading stops a running package's host the same way and starts it afresh, its restarts counted anew.

**One plugin id, one package.** A plugin's id is the first part of its sensors' keys, so two packages can't both provide one. When a host loads a plugin id another package's host provides, the package first in the order found (bundled before installed, then by folder name ignoring case) keeps it, whichever loaded first: the other package's host is stopped and the package fails with `duplicateId`, its message naming the id and the other folder, its sensors unavailable. It isn't restarted and its on or off is untouched; reloading it or turning it on tries again. Two plugins with one id inside one package: the second isn't loaded, and its error says why.

## Hosts

Each package runs in a process of its own: the engine's own executable, started as `InfoPanel --plugin-host --pipe <name> --plugin <dll> --log-dir <dir> --settings-dir <dir> --log-level <level>`, which runs the plugin host (`InfoPanel.Plugins.Host`) and nothing of the engine. The plugins inside a package's DLL share its host. The engine and the host talk JSON-RPC (StreamJsonRpc) over a named pipe the engine serves, for the current user only, named `ipph-{16 hex}` so its Unix socket path stays short.

- **Start.** Hosts start once the engine listens, after the built-in sensor sources, never inside their start-up wait. A host has 30 s to connect, 30 s to initialise its plugins and 10 s more to list their entries (without that list the engine goes on with none).
- **Restarts.** A host that exits or disconnects unexpectedly, or fails to start, is started again after 2 s, at most 3 times in 60 s (counted from the first failure); after that its package is failed, with the reason: the host's exit code and the end of what it wrote to stderr, or the last error. A stop the engine makes never restarts.
- **Stop.** One package's host is asked to shut down and given 5 s to exit, then killed (with its children) and waited for 5 s. When the engine stops, every host gets 2 s in all, in parallel, and the rest are killed before the engine exits; a stop that comes before the hosts have started means none starts.
- **The engine going away.** A host whose pipe ends without a shutdown (the engine crashed or was killed) gives its plugins 2 s to close and exits; one still alive 5 s after the pipe ended ends itself through the operating system, whatever threads or process-exit handlers a plugin left running (no managed code runs in that end).
- **Other operating systems.** The loader creates every plugin type in a DLL except one marked `[SupportedOSPlatform]` only for other operating systems, which it skips and logs, so a plugin built on a Windows-only library doesn't fail the others in its DLL. A DLL built for Windows as a whole (`net8.0-windows`) is still tried: most use portable APIs. The clock, the drives, the network, the volume and the system information, which the Clock, Drive Info, Network Info, Volume Info and System Info plugins read, are sensor sources of the engine (`infopanel.clock`, `infopanel.drives`, `infopanel.network`, and on macOS and Windows `infopanel.volume` and `infopanel.system-info`) with keys of their own, `infopanel:/clock/{entry}`, `infopanel:/drives/{drive}/{entry}`, `infopanel:/network/{interface}/{entry}` (the public address `infopanel:/network/public/{ipv4|ipv6}`) `infopanel:/volume/{device}/{entry}` (`default` for the default output device) and `infopanel:/system-info/{uptime|processes}/{entry}`; the weather, which the Weather plugin read from OpenWeatherMap with a key and a city each user typed, is the engine's weather source (`infopanel.weather`, [weather](weather.md)), `infopanel:/weather/{entry}`. The engine never answers the plugins' keys (`plugin:/clock-plugin/clock/{entry}`, `plugin:/drive-info-plugin/{drive}/{entry}`, `plugin:/network-info-plugin/{interface}/{entry}`, `plugin:/volume-plugin/{device}/{entry}`, `plugin:/system-info-plugin/{uptime|processes}/{entry}`, `plugin:/weather-plugin/weather/{entry}`), and a 1.x import binds them to the sources' ([import](../../spec/docs/import.md#plugins-the-engine-reads-itself)). A Weather plugin's settings file left in `plugin-settings/` is left alone. HWiNFO's gadget values, which the HWiNFO Registry plugin read, are a sensor source of the engine (`infopanel.hwinfo-gadget`) with keys of its own, by name: a binding to the plugin's keys (`plugin:/hwinfo-registry-plugin/{index}`) reads unavailable.
- **The runtime.** Plugins run on the engine's runtime, .NET 10, against the SDK the engine carries (net10.0). A plugin built for .NET 8 against 1.x's SDK loads as it is: the SDK binds by name (no version set, no strong name) and the host hands every plugin the host's copy, whatever copy the plugin carries, and that copy keeps every 1.x type and member (the tests load such a plugin, `InfoPanel.Plugins.TestFixture.V1`, built against `InfoPanel.Plugins.V1Sdk`, 1.x's SDK source).

## What a host writes

Only in the data folder, in the folders the engine gives it:

| File | What |
|---|---|
| `logs/plugins/{package}-{yyyyMMdd}.log` | The host's log, with its plugins' own lines (`PluginLog`, each message cut at 4,096 characters), at the engine's `logLevel`, daily, the newest 3 kept, 10 MiB a file; never the console |
| `plugin-settings/{package}/{plugin id}.json` | A configurable plugin's settings, a flat map of its keys and values, written to a temp file and renamed over it |

A settings change is logged by its key, never its value (settings can be secrets, such as an API key). A plugin that fails to apply a setting leaves an error with only the setting's key, the failure's kind and its time, never the plugin's message, which could hold the value. A reload or restart of the package's host during a settings change answers the change 409: a value checked against one host's settings is never sent to another. Nothing goes to 1.x's folder (`{LocalApplicationData}/InfoPanel`), which 1.x's host wrote its logs and settings to. Before each start of a host, the engine checks the folders it gives it: a package's settings folder or the log folder that is a link, or one of the package's log files that is a link, or a folder that with links resolved is in the 1.x folder (as start-up checks the data folder's own entries), fails the package at once, with the reason, and no host starts. Plugins run as the user, who can write to the 1.x folder anyway, so this check guards against a misconfigured folder, not against a hostile plugin.

## Sensors

Every entry a package's plugins list is a sensor of the `plugins` source:

- **Keys** are 1.x's: `plugin:/{plugin id}/{container id}/{entry id}`, or `plugin:/{plugin id}/{entry id}` for an entry in an ephemeral container.
- **Group** is `{plugin name} › {container name}`; **name** the entry's; **unit** the sensor's (empty for texts, tables and pictures).
- **Readings:** a sensor's value, minimum, maximum and average as the plugin reports them; a number that isn't finite (NaN, which a plugin sets when it doesn't know the number, or an infinity) has no reading, so its key reads `unavailable` ("–" on a panel) while the package's other keys stay live, and reads again with the next finite value; a minimum, maximum or average that isn't finite beside a finite value reads as the value. The SDK's `PluginSensor` leaves values that aren't finite out of its minimum, maximum and average. A text's text; a table's rows, read by a scene's table input as `docs/bindings.md` says, its text the first row's cells.
- **Pictures** (`PluginImage`, 2.0 only) are `image` sensors ([API](../../spec/docs/api.md#sensor-pictures)): the reading is the picture's reference, 16 hexadecimal digits of its SHA-256, new with each new picture, and no picture (`Clear()`) is no reading. The entry names the `plugin` media provider (`provider`), which draws the picture for a scene's `media` node whose reference is a text input bound to the sensor, reaching no address ([providers](../../spec/docs/providers.md)); a client gets its bytes with `GET /api/sensors/image`. The engine keeps each image entry's current picture and the one before it (an item holds the previous one while the next loads), in memory only; a stopped or failed host's pictures go with its readings, a restarting host's stay, stale, until its new catalogue, which starts them afresh.
- **Status** follows the package's host: `live` while it runs (plugins send changes only, so an unchanged value is still live), `stale` while it restarts (the last values kept), `unavailable` once it is stopped or failed. A key under a plugin id a package provided in this run but that names no entry is `unavailable`; a key under any other plugin id is left to the other sources (unavailable, or simulated in mock mode).
- **Plugin ids** that are empty, contain `/`, are longer than 64 characters or start with `infopanel.` (the engine's own sources) are refused; an id another package provides follows the one-id rule ([above](#on-off-and-reload)), so keys stay unique. So is the id of a plugin whose sensors the engine reads itself now, from any package (an old copy of the retired bundled package under another folder name), so its keys don't come back half live: `clock-plugin` ("its sensors are built into the engine now (the Clock source)"), `drive-info-plugin` ("… (the Drives source)"), `network-info-plugin` ("… (the Network source)"), `volume-plugin` ("… (the Volume source)"), `system-info-plugin` ("… (the System Info source)") and `weather-plugin` ("… (the Weather source)"). A plugin whose containers or entries have an id longer than 256 characters, or that would make a key longer than 512 (as long as a document's sensor key may be), is refused too, before any of its keys is made. A refusal is logged as the package's error.

## Bounds

Plugins are code the user chose to run, but a buggy one must not take the engine's memory. A message over 16 MiB from a host closes its connection (the host restarts by the policy), and so does a host that has more than 1,024 messages, or 32 MiB of them, waiting for the engine to handle them (it handles a host's messages one at a time, in order). A host's calls to the engine are notifications: one that asks for a reply closes its connection too, so the engine never holds replies a host doesn't read. One the engine doesn't take (another method, or arguments it can't read) is dropped as it is read, with one warning per connection, and never counts against those limits. A host's plugins list at most 16,384 entries; the rest are left out, with one warning. Names, groups and units are cut at 256 characters, texts at 4,096, tables at 1,000 rows, 64 columns and 1,024 characters a cell, each with one warning per entry. A table's column names are made unique, ignoring case (an empty or repeated name gets `#` and a number no other column has), and a table the engine can't read is left without a value, with one warning, while the rest of the update is applied. A host's stdout and stderr are read as they come, in chunks of at most 4 KiB rather than as lines: stdout is dropped (the host logs to its file), and only the last 4 KiB of stderr are kept, for the reason a host failed.

**What a host sends.** The host holds everything it sends the engine to one budget, sized so the engine holds 5 s of it while it handles nothing: at most 16 MiB at once and 3 MiB a second after, and 64 messages at once and 32 a second after (in any 5 s, 31 MiB and 224 messages, within the 32 MiB and 1,024 above). Within it, its messages of readings take at most 8 MiB at once (one message, the most it puts in one) and 2 MiB a second, and its pictures at most 12 MiB at once and 2 MiB a second, so neither keeps the other from the engine. Readings that find no room wait, and go when there is with their newest values, the changes that waited longest first; an error report or the host's processor use that finds none is dropped (the host's log keeps errors). Each counts by the host's estimate of its bytes, an upper bound.

**Pictures.** A plugin's picture is a PNG, JPEG, GIF or WebP of at most 8 MiB; the host leaves a larger one out, as no picture, with one warning. The host sends a picture only when its SHA-256 changed (it hashes an entry's picture at most once a second), alone in a message, as base64 (an 8 MiB picture is about 10.7 MiB); an entry sends at most one new picture a second, counted from the end of its last send, and a waiting picture is replaced by the entry's newer one. The pictures that waited longest go first, and one still waiting for its hash keeps its place, so younger pictures can't take the room it waits for. Each picture counts its base64 and 4 KiB for the message around it; the host's pictures come to at most 12 MiB at once and 2 MiB a second, and 16 at once and 16 a second. The engine admits a picture only for an image entry its host listed, from a host that isn't stopped or failed, and within the same rates with 5 s more burst (a stall can hand them over at once): an entry 6 at once and one a second, a host 22 MiB at once and 2 MiB a second, 96 pictures at once and 16 a second. It knows a picture's size from its base64's length and refuses one over 8 MiB before decoding it; past the rates a picture is refused, as no picture, with one warning for the host. An admitted picture is inspected as an asset is (a PNG, JPEG, GIF or WebP within the media limits; anything else is refused, as no picture, with one warning for the entry). A host's pictures, each entry's current and previous, come to at most 64 MiB; past it a new picture is refused, as no picture, with one warning. A picture of a host that has since stopped, failed or been replaced is never taken.

## Errors, processor and memory

A plugin's errors (an action that throws among them), a refused plugin, a failed start and a restart are logged as warnings, `plugin {package}/{plugin id}: …` (the recent log entries carry them), and a package keeps its newest 20, each with the time the engine got it and the plugin it came from (none for the package's own). A package's processor use is its host's own report (every plugin's is the process's), while it runs, counted as the engine's own CPU is ([API](../../spec/docs/api.md#sensor-sources)): on macOS and Linux per CPU, as Activity Monitor and `top` count it (100 is one busy CPU, up to 100 × the logical CPUs); on Windows a share of the whole computer's, 0–100, as Task Manager counts it. Its memory is read by the engine from the host's process as the engine's own is, as the operating system's tool shows it: the physical footprint on macOS, the private working set on Windows, the resident set on Linux.

## The API

A client lists the packages and works them through the engine API ([api.md](../../spec/docs/api.md#plugins), the session's `plugins` feature): `GET /api/plugins` lists each package with its state, its plugins, its actions and its newest errors, and never a setting's value; `PUT /api/plugins/{folder}/on` turns a package on or off; `POST /api/plugins/{folder}/reload` reloads it; `POST /api/plugins/{folder}/open` opens its folder, and `POST /api/folders/plugins/open` the data folder's `plugins/` (created when it isn't there); `GET /api/plugins/{folder}/plugins/{id}/actions/{method}` answers an action's state and `POST` runs it, an action the plugin lists and no other method ([below](#actions)); `GET` and `PATCH /api/plugins/{folder}/plugins/{id}/settings` read a plugin's settings from its host and change one, the value checked against the setting first. Every call to a host is answered within 10 s. Packages are still found only when the engine starts.

### Actions

A plugin's actions are its public methods marked `[PluginAction]` with no parameters; the host runs no other method. A plugin may describe each one (`IPluginActionStates`, [PLUGINS.md](../../PLUGINS.md#action-states-and-confirmation-20)): whether it can run now, one line of its state (at most 256 characters), and a confirmation, a title (at most 256) and plain text (at most 4,096), which a client shows before it runs the action; the host cuts each to its limit, and an empty title is the action's name. A plugin that doesn't (every 1.x plugin) has every action enabled, with no state and no confirmation. The host asks the plugin on a task of its own and waits 5 s at most: a state that throws or doesn't come is disabled, saying so, and reported as the plugin's error once until it answers again. An action's state is asked once at a time: requests that come while the plugin still hasn't answered wait for that answer (each 5 s at most), so a plugin that hangs holds one task, not one a request.

Running an action, the host asks its state first and runs it only when it is enabled: the task that runs it decides immediately before calling the method, and the host answers once it has. It doesn't start the action once the engine has given up on the call (its 10 s), 8 s after the call reached the host (so an answer that comes too late for the engine never leaves an action running), or once the host has begun to shut down; the engine answers 202 once the host has started it, and 409 when it can't run now or wasn't started (it isn't run). The action runs on a task of its own, so a long one holds neither the host's other calls nor its other actions, and its state reads `running` until it returns (an action that returns a task, until the task ends; runs of one action at once each count, so until the last ends). Shutting down, the host waits up to 1 s for the actions under way to end before it closes the plugins. The engine never asks the confirmation itself: that is the client's.

## Panel packages

A panel package adds USB panel families: a folder `InfoPanel.{Name}` (as a plugin package's, at most 128 characters) holding `InfoPanel.{Name}.dll` and a `panel.json`, in the same two folders, bundled ones first. A folder with a `panel.json` is a panel package and never a sensor plugin's: a package holds one or the other, and the frameworks differ too (panel drivers target **.NET 10** through `InfoPanel.Panels.Sdk`, sensor plugins **.NET 10** through `InfoPanel.Plugins`, and one project references one SDK). A release bundles the panel driver projects (`InfoPanel.Panels.{Family}`, every one with a `panel.json`) in `{engine folder}/plugins/`. Writing a driver: [PLUGINS.md](../../PLUGINS.md#panel-drivers); what the engine does with it: [panels](panels.md).

The engine reads every `panel.json` when it starts, bounded as `PluginInfo.ini` is (a regular file, not a link, at most 64 KiB, JSON at most 16 deep; opened once without following a link, its type checked on that handle, so a link put there after the check is refused), so a family is known before any host runs, even while its package is off:

```json
{ "format": "infopanel.panel-package/1", "sdk": "1.0",
  "families": [{ "id": "virtual", "name": "Virtual panel",
    "match": [{ "usb": "1209:0001" }, { "usb": "1209:0002", "transport": "serial" }],
    "models": [{ "id": "480x320", "name": "Virtual panel 480 × 320", "width": 480, "height": 320, "v1Model": null }] }] }
```

- `sdk` is the panel SDK's `major.minor` it was built for: the engine runs a package of its own major and a minor no higher than its own (1.0 today); any other is failed, `sdk`, and starts no host.
- `families`, 1 to 16: `id`, a lower-case letter and at most 31 letters and digits, stored with every panel of it and never renamed; `name`, 1 to 64 characters, which a client shows for a family it doesn't know; `match`, 1 to 64 devices by USB `vendor:product` in lower-case hexadecimal, with an optional `transport` (`usb`, `serial`, `hid`) and `interface` (0 to 255); an optional `detect`, at most 64 patterns, each `usb` a vendor in lower-case hexadecimal and its products as four lower-case hexadecimal digits with `?` for any digit, or `*` for any product (`0416:54??`, `87ad:*`): a device one names that no family drives is listed as detected ([panels](panels.md#detected-not-supported)); `models`, at most 512, each `id` and `name` (1 to 64 characters), `width` and `height` (1 to 16384), an optional `v1Model`, the model's name in 1.x, and optional `v1Aliases`, at most 16 other names 1.x saved it under (1 to 64 characters each; a 1.x panel saved under one comes over as this model); and an optional `settings`, at most 32 settings of the family's own for its panels, each `id` (a lower-case letter, then at most 31 letters and digits), `name` (1 to 64 characters), `type` and `default`: `boolean`; `enum`, with `values` (1 to 64, each `id` and `name`) and a `default` among them; `integer`, with `min` and `max` and a `default` between; `string`, at most 64 characters; or `model` (its id `model`, its default null: the model a panel whose handshake names a model the family doesn't declare is tried as), each with an optional `v1Field`, the element of a 1.x panel device its value comes from. A panel's values reach the driver in `PanelOpenOptions.FamilySettings` (an object of the values set, an `integer` always as a whole number; one not set takes its default, which the driver reads from its own `panel.json`; a value kept of a setting the package no longer declares comes after the declared ones, so a driver skips members it doesn't know; a kept value a setting declared again doesn't take, another type, comes as that setting's default); a change of any opens the session again, a change of none doesn't. Members it doesn't know are left alone.
- A family id is unique: one a built-in family has (`beadapanel`), or a package earlier in the order declares, refuses the later package whole (`duplicateId`, logged), and its families aren't known. A `panel.json` that isn't one is skipped with a warning.

A panel package is on unless the user turned it off in `plugin-state.json`, as a plugin package is; one that is off starts no host, and its panels are `off` with the reason `driver`. `--no-plugins` runs no panel package either. Its host is the engine executable again, `InfoPanel --panel-host --pipe <name> --package <dir> --log-dir <dir> --log-level <level> --engine-pid <pid> --engine-start <its start time>`, one a package, connected over a pipe for the current user only and never elevated, started when a device its families name is plugged in and stopped once none is and no session is open; it writes only its log (`{data}/logs/plugins/{folder}-{date}.log`), and ends once the engine's process is gone, watched before any package code loads (by its id and start time, as the sensor helper watches it, so a process that took the engine's id isn't taken for it). The host makes each driver through its public constructor that takes the device seam (`IPanelDevices`), given its own (libusb, HidSharp and `System.IO.Ports`, [panels](panels.md)), else through the one that takes nothing. A DLL without a driver for every family its `panel.json` declares isn't loaded, and a host whose drivers aren't those families (or whose hello is malformed) fails its package at once. A host that ends unasked is started again after 2 s, at most 3 times in 60 s, after which the package is failed until the engine restarts. Its messages are bounded (64 KiB each, at most 64 kept waiting for their answers) and frames never cross the pipe: they go through a file of two slots in a folder of the run folder, checked as the run folder is (not a link, this user's alone) before anything in it is swept ([panels](panels.md)). A host that doesn't take a request within its deadline (each one has one, a close the engine sends unasked included), or can't close a session within its budget, is ended and started again. On quit, its sessions close within the panels' 3 s bound and the host is killed past it; a host start still under way then is cancelled, so no host process is created after the stop. Its families and its state are in the Devices API's `families` ([api.md](../../spec/docs/api.md#panel-families)); `GET /api/plugins` doesn't list panel packages yet, so one is turned off in `plugin-state.json` while the engine is stopped.

# USB panels

The engine drives small USB screens (panels) itself: each shows one profile, live, as the preview does. BeadaPanel is the first family; others follow.

## What is driven

- **BeadaPanel**, every model InfoPanel 1.4 knows (21; their ids, `2` to `Z`, are in `InfoPanel.Core/Panels/BeadaPanel/BeadaPanelModel.cs`), over USB through libusb-1.0, as InfoPanel 1.4 speaks to them byte for byte: the info query, the start sequence, frames in RGB565, brightness, and the screen turned off when a panel stops. Panels known to decode JPEG get JPEG frames instead (below), about twice the frame rate on a 1920 × 480 panel.
- **libusb-1.0** is looked for, by full path: beside the engine, then in the folder `INFOPANEL_LIBUSB_DIR` names (a full path), then on macOS in `/opt/homebrew/lib` and `/usr/local/lib`, and on Linux the system's `libusb-1.0.so.0`. Without it panels are unsupported, with one line in the log, and nothing else changes. The Mac app and the Windows installer carry it beside the engine ([packaging.md](packaging.md)); an engine built from source on macOS finds it after `brew install libusb`.
- **Another program holding a panel** keeps it: the engine never resets a device or takes it from a driver, sets its configuration only when it has none, and a panel it can't claim is tried again every second with one line in the log.
- **`--no-panels`** turns all of it off: no USB device is listed, opened or written.

A family is a driver behind one small interface, in the `InfoPanel.Panels.Sdk` assembly (.NET 10): `IPanelDriver` names the USB vendor and product ids it drives, tells its own panels by a probe and opens a session; `IPanelSession` writes a frame and answers the time the device took for it (the pace learns from that time), sets the brightness, and closes with the screen turned off within the stop's budget. The engine lists the devices and offers each only to the drivers whose ids match it, in order: the first whose probe answers "mine" keeps it until it is unplugged, one that couldn't ask (busy, a probe that throws, or one still waiting on the device at its 5 s deadline) is offered again a second later, and a device no driver names is never opened. A probe is cut short when the engine stops or the computer sleeps, and a session that fails to close still lets the panel go. The engine still renders, turns, encodes and paces every frame, keeps `devices.json` and answers the API. BeadaPanel's driver is built into the engine (`BeadaPanelDriver`, its protocol unchanged); every other family comes from a panel package ([plugins](plugins.md#panel-packages)), and the log names the driver that takes a device (`driver beadapanel, built in`, `driver turing, the panel package InfoPanel.Panels.Turing`).

A package's drivers run in a panel host, a process of its own (the engine executable with `--panel-host`, one a package, run as the user over a current-user pipe), started when a device its families name is plugged in and stopped after the last one leaves. To the engine a hosted driver is one more `IPanelSession`, a proxy (`InfoPanel.Core/Panels/Hosted/`), so one runner and one pacer serve both kinds. No frame crosses the pipe: each session has a file of two frame slots in the run folder, private to the user, which the engine writes and the host maps read-only; a `write` message hands a slot to the host until its answer, the engine filling the other meanwhile, and with both still held a frame is refused as a timeout. A write the host hasn't answered within 5 s is a timeout too. Every call goes through the host's connection as it is then: a host that ends unasked is started again after 2 s, at most three times in a minute, and its panels' sessions start again on the new one (the reason `driver` meanwhile); after the third the package fails and its panels are `failed` · `driver`. A package turned off leaves its panels `off` · `driver`, and a saved panel whose family no driver declares is `failed` · `driver`. On quit the panels close within the 3 s bound, then each host is asked to end in what is left of it, and killed past it. A spare engine can list virtual devices in place of the computer's (the `Engine:VirtualPanels` setting, a count) for the virtual panel package, a test fixture that is never shipped (`InfoPanel.Panels.Virtual`, family `virtual`, device `1209:0001`). Its `panel.json` declares a boolean, an enum and a `model` setting, and a `virtual-mode.txt` beside its DLL with the line `unknown-model` makes its probe name a model the family doesn't declare (`pm-47`), which runs only once the panel's `model` setting names `480x320` ("Try it as…", [api.md](../../spec/docs/api.md#family-settings)).

A driver reaches its device only through the SDK's device seam, `IPanelDevices`, which its public constructor takes (the panel host passes its own; a driver whose constructor takes nothing has no devices): the engine's (`InfoPanel.Core/Panels/Devices/EnginePanelDevices.cs`) gives a device's cached descriptors without opening it; claims a USB interface through libusb as BeadaPanel's are claimed (configuration 1 only on an unconfigured device, never a reset or a kernel-driver detach, another program's device answering `busy` or `access` with nothing written), transfers only on that interface's bulk endpoints in the call's direction (any other endpoint answers `notSupported`, nothing sent), and sends a zero-length packet after a write only when the driver asks and the write fills its last packet (BeadaPanel's own path never does); opens a HID collection through HidSharp with its lock across processes, so two of InfoPanel's panel hosts never share a panel (HidSharp opens a collection shared, as 1.4.x did: on Windows another program driving the same panel at the same time isn't kept out, as in 1.4.x), chosen by the device's ids, then (where the system says which USB port each collection is on: Linux, macOS) its port and its device's bus and address (a device plugged in again, or another in its place, has a new address: `gone`; a device whose bus or address can't be read is refused, `busy`, with a line in the log, since it can't be told from another in its place), then the driver's filter (interface, output report length, usage page), and where the system doesn't (Windows) by physical device (a composite device's collections are one device): the driver's filter first, then the first device of those ids not given to another panel, given to this one until its last collection closes (a single device too, so an identical one plugged in later goes to the next panel; a driver trying its collections in turn keeps its device), logged, the rest answering `busy`; a collection opened is checked again in a listing made after the open, before anything is written, and one whose device has changed is closed, `gone` (Windows gives no address: a device of the same ids in the same port without a serial is the same model in the same place, taken as the same panel); and opens a serial port through `System.IO.Ports`, found by the device's own identity and checked to be the device the engine listed, never "the first port": on Linux in sysfs (the device at its port with its ids, bus and address, then its interfaces' `tty`), on macOS in the IORegistry (`ioreg`: the USB device at its location id with its ids and address, then the `IOCalloutDevice` below it), on Windows in the device tree (the COM port of the only present USB device of its ids when it is in the device's own USB port (its location path's port numbers are the device's) and, when both serial numbers can be read, has its serial number; or of the one of them whose serial number, which Windows makes its instance id, is the device's; several that can't be told apart are refused, `busy`, with a line in the log: "several identical devices without serial numbers; unplug the others or use one at a time", and so is one whose port the system doesn't say; a device of the same ids in the same port, plugged in in its place, is the same model in the same place and is taken as the same panel, as Windows' HID collections are); another device there now answers `gone`. The port is opened with DTR and RTS off and nothing written, then checked to be the device's from the opened port itself (Linux: the open descriptor's character device up through sysfs to its USB device's ids, bus and address; macOS: the descriptor's device number against the device's callout node's; Windows: the COM name against the device's), and only then are its lines set as the driver asks (not once the open's timeout has passed or it was cancelled during the check: the port is closed with its lines untouched); a port that is another device's is closed at once, `gone`. Opening a tty on Linux may still raise DTR for that moment, as the OS does on every open. Each call keeps to its one timeout, counted from the call: an open (the descriptor lookup, the HID listing and the port's lookup included) answers `timeout` once it has passed, and a handle that opens later is closed; a cancel throws, the same; a call waiting for another on the same handle waits only within its own timeout (then `timeout`, nothing sent; a cancel while it waits throws), and the device gets only what is left. Reads wait in 100 ms slices, so a cancel or a dispose ends them within one; a USB read gathers what comes until its buffer is full, a short packet ends it or its time is up, and a zero-length packet gets only what is left of its write's time. Disposing a HID or serial handle ends the call under way at once (it answers `io`), and disposing any handle answers the calls waiting for their turn on it `io` at once (one whose own token is cancelled first still throws); a serial port's dispose throws away what is queued both ways first and closes the port in the background (the port can't be used after); a USB write, which libusb's synchronous transfers can't cut short, ends at its own timeout (a frame's, under a second at the families' rates) and the interface is released then, a new open of the device meanwhile answering `busy`; the dispose returns within 200 ms either way. A zero-length packet with no time left isn't sent (`timeout`).

What the engine does with a family's frames comes from its session's capabilities, in 1.4's order (its Thermalright code's): the frame turned and fitted to the panel; dimmed in software when the panel has no light of its own (`DimInSoftware`: each colour times the brightness, as 1.4's Thermalright, Thermaltake and JL panels were); the driver's overlay for the rotation drawn over it (`Overlays`, a PNG a rotation, its alpha kept: 1.4's display masks); cropped (`Crop`: rendered at 480 rows, the top 462 sent, 1.4's flicker fix); then encoded. The formats are JPEG, RGB565 little-endian (`Rgb565Le`, BeadaPanel's, Skia's conversion as before), and RGB565 little-endian truncated (`Rgb565LeTruncated`, 1.4's Thermalright conversion), RGB565 big-endian, RGB888 and BGR888, each by truncation (a channel's low bits dropped, never rounded or dithered, as the vendors' own tools do). An overlay is checked by the size its PNG header declares before anything decodes it: the panel's own size, else the session isn't started. A JPEG over the panel's `MaxFrameBytes` is encoded again `JpegQualityStep` lower (5 by default) down to `MinJpegQuality`, logged once a session; one still over it at the floor isn't sent (the driver never gets more than its cap), and the panel keeps its last frame, logged once a session, which a keep-alive due still sends. The last frame is sent again after the session's `KeepAliveEvery` without a new one (1 s when it gives none). A panel's own frame rate (`frameRate`, 1 to 60, in place of the engine's; below) and a family's own settings (its `panel.json`'s `settings`, below) are the panel's; a change of a family setting closes its session and opens it again with them.

## How it runs

- Every second the engine lists the USB devices. A BeadaPanel it hasn't seen is identified by its info query and matched to the panels it saved, by serial, else (a panel without one) by its USB port. Panels that report the same serial are told apart by the port each was last seen at; one that still can't be told apart (at a port none of them had) is listed as a new panel, with a line in the log. A new one is saved **off, without a profile**: the log says `BeadaPanel {model} found, serial …, at {port}: saved, off`.
- A saved panel runs while it is plugged in, turned on, and its profile exists and can be drawn. It shows the profile at its own size: turned by its rotation, scaled to fit and centred, the rest black. Frames come at the panel's own frame rate when it has one (its `frameRate`, 1 to 60), else the engine's (Settings › Engine), slowed to what the panel takes and never past its own ceiling, and the panel's own thread keeps to that pace at every write, whatever the frame rate. A panel keeps frames of its own before it shows them, and a write returns once the panel has taken the frame, not when it is shown; once that store is full, each write waits for the panel to show a frame, and every change is shown that whole store late (seconds on a BeadaPanel 8). The engine can't see how full the store is until it is full, so it stays under what the panel is known to show and only the writes lower it: a T113 panel (the BeadaPanel 8 and its kin) is sent at most 15 frames a second as JPEG and 12 raw, under the 17–20 and 16 it was measured to show; any panel is sent at most 85 % of what its thread can write (a panel that needs 48 ms a frame is sent at most 17 a second), so a stream whose writes are long by nature, as raw frames are, stays under what the panel shows; when the writes take well over their unloaded time (the shortest write after the thread had been waiting for a frame) and keep the thread busy, in 2 of 5 seconds, it measures how many frames a second the panel took, sends half that for a second so the store drains, then at most 85 % of it. After a few quiet seconds that most rises one frame a second, but never past the most frames a second the panel was sent for 8 quiet seconds in a row, on a T113 as on any panel, nor past a T113's 15 or 12, and only while the frames are no slower to write than they were then; once it has been lowered again after rising, it stays there. What it learned is forgotten when the panel starts again and when the frame rate setting changes. So a change is usually shown a frame or two after it is written, but a panel's store can still fill: a panel other than a T113 once when it is sent more than it shows from the start (until that is seen: a few seconds, longer if it is only a little slower), and any panel once after a rise, when it shows the content of the moment more slowly than the most it rises to; a change then waits behind the store until it drains. The frame rate setting stays the most a panel is sent. A frame that didn't change isn't sent, and the last one is sent again every second.
- The screen goes off (backlight off, a black frame, the stream's end) whenever a panel stops: turned off, unplugged, its profile deleted, or the engine quitting (at most 3 s for every panel together, counted from the quit). A deleted profile leaves the panel off, its profile kept, until a profile with that id comes back. Changing a running panel's profile moves it to the new one without turning the screen off.
- **Frames as JPEG.** A panel's `encoding` is `auto` (the default), `jpeg` or `raw`. `auto` streams JPEG to the panels it has been seen to work on: a BeadaPanel on the T113 platform with PanelLink 2 or later (the BeadaPanel 8 and its 1920 × 480 kin); every other panel gets raw RGB565, as 1.4 sends it. Each frame is one JPEG at quality 90, encoded from the turned and fitted frame, and the stop's black frame is a JPEG too. On a BeadaPanel 8 that is about 35 frames a second against raw's 16, for some 3–4 ms of encoding a frame. A panel that doesn't take the JPEG stream's start has its stream reset, as at the start, and is sent raw instead, with one line in the log, and stays raw until the engine restarts. `jpeg` tries JPEG on any panel, for one that isn't known yet; `raw` never does. After a JPEG stream ends, a BeadaPanel 8 takes no new stream for 20 to 30 s (another family's JPEG panel has no such wait), so a panel turned off and on again, or set to another encoding, starts again 30 s after its JPEG stream ended, its state `starting`, with reason `settling`, until then (another engine started on the panel sooner retries until the panel answers).
- Unplugged, a panel stays saved; plugged in again it is found and runs again: in any port when it has a serial of its own, at the port it was saved at when it has none (or shares its serial with another saved panel).
- The log shows each panel starting, its frame rate and time a frame 10 s after it starts and then every 5 minutes, and why one failed (it is tried again every second). It also has a line for each change of a profile's document (`Profile …: changed (Commit) rev 12`), one when a panel writes the first frame of a new revision (`Panel …: wrote rev 12, encode+write 6.1 ms`), and one when a panel's pace changes by more than a fifth, at most every 5 s (`Panel …: pacing 9 fps (writes 48.3 ms, unloaded 4.5 ms)`).

## `devices.json`

The saved panels are in [`devices.json`](data-folder.md#the-panels) in the data folder:

```json
{"format": "infopanel.devices/1", "devices": [
  {"id": "0f8e4a52-6c1b-4f38-9a57-2d1c3b4e5f60", "family": "beadapanel", "model": "8", "serial": "934072005c00481401044f2420751fd6",
   "port": "0-1", "enabled": false, "profileId": null, "rotation": 0, "brightness": 100, "encoding": "auto"},
  {"id": "6d2a7c1e-3b4f-4a5d-9e8f-0a1b2c3d4e5f", "family": "virtual", "model": "480x320", "serial": "VIRTUAL1",
   "port": "virtual-1", "enabled": true, "profileId": null, "rotation": 0, "brightness": 100, "encoding": "auto",
   "frameRate": 10, "familySettings": {"look": "framed"}}
]}
```

`frameRate` (1 to 60) and `familySettings` (the family's settings the panel has set, in the family's order) are written only when set. Clients read and change it through the engine's devices API ([api.md](../../spec/docs/api.md#devices)): `GET /api/devices` lists the saved panels with their state and settings, `PATCH /api/devices/{id}` changes a panel's `enabled`, `profileId`, `rotation`, `brightness`, `frameRate` and family settings (saved and applied at once; a family setting by opening its session again), and `DELETE /api/devices/{id}` forgets a panel (its screen goes off; still plugged in, it comes back as a new panel, off). `POST /api/devices` saves a panel that need not be plugged in; one a client brings over from 1.x carries `v1`, the 1.x device's `deviceId` and `deviceLocation`, kept in the file, so the same 1.x device is never saved twice. `encoding` is set only in the file.

## Turning a panel on

A client turns a panel on with `PATCH /api/devices/{id}`, its `enabled` `true` and its `profileId` the profile to show. Without a client, in the file:

1. Plug the panel in with the engine running, and wait for its `found … saved, off` line in the log.
2. Quit the engine.
3. In `devices.json`, set the panel's `enabled` to `true` and its `profileId` to the id of the profile to show (the profile's folder name under `profiles/`). Optionally set `rotation` (0, 90, 180, 270), `brightness` (0–100) and `encoding` (`auto`, `jpeg`, `raw`).
4. Start the engine: the panel lights up within a second or two.

A file the engine can't read (not JSON, a value out of range) is left as it is, and panels stay off for that run, with the reason in the log. An `encoding` it doesn't know reads as `auto`.
